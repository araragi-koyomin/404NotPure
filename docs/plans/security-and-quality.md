# 安全边界、测试、数据库与前端质量计划

## SEC-001：认证与授权

以下是 SEC-001 开始前的缺陷基线与合并后仍保留的边界，不能把已经修复的条目继续描述成当前缺陷：

- 剩余边界：Spring Security 配置仍是 `anyRequest().permitAll()`，授权依赖 MVC 拦截器和控制器/服务层判断，边界分散；
- 历史缺陷：拦截器曾放行 `/api/orders`、`/api/cart`、`/api/products` 等整个前缀；PR #5 已改为按 HTTP 方法和精确路径判断公开接口；
- 历史缺陷：注册请求曾允许提交 `role`；现已改为服务端固定创建普通用户，资料更新保留数据库中的既有角色；
- 历史缺陷：购物车更新/删除曾未验证条目归属，支付表单曾未验证订单归属；PR #5 已补账户、购物车和支付表单所有权校验及真实 MySQL/MockMvc 测试；
- 历史缺陷：JWT 签名密钥曾硬编码，Cookie 与 JWT 生命周期曾不一致；现已迁移到必填 `JWT_SECRET` 并统一有效期；
- 历史缺陷：`LoginInterceptor` 曾只读取 Cookie，而 `TokenUtil` 和 Axios 还支持 `token` 请求头；现已统一单来源、相同双来源和冲突双来源规则；
- 剩余边界：Spring Security 仍是 `anyRequest().permitAll()`，具体认证和资源权限由 MVC 拦截器、控制器和服务层共同承担；CSRF 仍关闭，由 SEC-012 单独处理；
- 历史前端登录页面会把完整登录响应和账户响应输出到浏览器控制台；登录响应数据包含 token，账户响应包含角色、电话等资料。旧运行归档曾错误写成已删除，本轮已由 SEC-011 修复并建立自动化防回归检查。

SEC-001 当时先写权限矩阵失败测试，再统一 Security/拦截器职责；测试覆盖未登录、普通用户、管理员、资源所有者和跨用户访问，而不是只断言 `validateAdminRole` 被调用。后续 SEC-012 修改认证结构时必须保留这些回归证据。

### 2026-08-10 已确认的 SEC-011/SEC-001 开发基线

项目所有者确认 SEC-011 与 SEC-001 使用同一开发分支 `fix/auth-boundary-and-sensitive-logging`，从 `master@6592fe27` 开始并严格按 SEC-011 → SEC-001 顺序处理。计划合并目标为个人 Fork 的 `master`；实现、测试和独立审查完成前不提交、不推送、不创建 Pull Request。

已确认权限决定：

- 管理员不能替其他用户发起支付；普通用户和管理员都只能为属于自己的 `PENDING` 订单生成支付表单。
- 浏览器暂时保持现有兼容方式，同时发送 HttpOnly Cookie 和精确名称为 `token` 的请求头；单独使用任一来源都允许，两者同时存在时必须相同，值不同或存在多个冲突值时统一拒绝，不能让拦截器和控制器采用不同身份。
- CORS 由反射任意 Origin 改为明确前端来源白名单；认证 Cookie 增加 `SameSite=Lax`。CSRF 本轮仍保持关闭，不把“尚未建立 CSRF token 前端协议”伪装成已经解决；后续由 SEC-012 完成前端 token、公开登录/注册和支付宝 notify 例外的兼容设计与测试。
- JWT 签名密钥迁移为环境变量配置，真实 `.env` 不读取也不修改；测试使用专门的伪密钥。JWT 与 Cookie 使用同一个可配置有效期。
- `PATCH /api/accounts/{username}/points` 当前没有可信业务授权规则，且没有前端调用证据。本轮保持拒绝并由 ACCT-001 单独定义，不能因为移除旧拦截器路径判断而意外允许用户自行设置积分。
- 购物车零数/负数问题未混入 SEC-001。CART-001 已通过 [PR #21](https://github.com/araragi-koyomin/404NotPure/pull/21) 合并：添加和修改只接受严格正整数且不超过当前可用库存，V5 增加数量检查和用户商品唯一约束，列表批量返回库存状态，前端跳过不可结算商品；完整证据见[购物车数量与库存状态交付记录](../archive/2026-08-16-cart-quantity-integrity-delivery.md)。支付成功后的购物车清理仍属于 PAY-002。

建议分层职责：MVC 拦截器只负责精确公开路由和是否登录；`TokenUtil` 集中解析并验证认证来源；控制器和服务负责购物车、订单等具体资源所有权；商品、库存、广告继续保留管理员角色检查；支付宝 notify 是精确公开的外部回调。Spring Security 本轮不大规模改写成另一套 JWT 过滤器，避免形成互相矛盾的双重认证实现。

本轮权限矩阵如下。这里的“公开”只表示不要求商城用户 JWT，不表示可以跳过接口自身的签名、参数或业务校验。

| 请求 | 未登录 | 已登录非所有者 | 资源所有者 | 管理员 | 额外规则 |
|---|---|---|---|---|---|
| `POST /api/accounts`、`POST /api/accounts/login`、`POST /api/accounts/logout` | 允许 | 允许 | 允许 | 允许 | 退出只使浏览器 Cookie 过期；注册仍由服务端固定普通用户角色 |
| `GET /api/products/**` | 允许 | 允许 | 允许 | 允许 | 只放行 GET；同前缀的创建、更新、删除仍需登录且保留管理员校验 |
| `POST /api/orders/notify` | 允许 | 允许 | 允许 | 允许 | 支付宝服务器入口；仍必须通过 RSA2 验签、应用/收款方、金额、状态和事务校验 |
| `GET /api/orders/returnUrl` | 允许 | 允许 | 允许 | 允许 | 只做浏览器跳转，不证明支付成功；PAY-002 仍未完成 |

## JPA-001：关闭 Open Session in View 前明确数据读取边界

Open Session in View 是 Spring Boot 默认开启的一种 JPA 行为：HTTP 请求生成响应期间，数据库会话仍保持打开，因此控制器或 JSON 序列化阶段也可能临时读取尚未加载的关联数据。它能暂时掩盖服务层没有完整读取数据的问题，也可能把数据库查询推迟到响应生成阶段。当前商品规格、商品详情图和广告关联使用延迟加载，所以不能直接关闭该选项后假设接口仍然兼容。

处理顺序：

1. 为商品详情、广告详情、订单详情和订单列表接口补充接口级测试，确认响应字段和查询结果。
2. 在 Repository 查询或带事务的服务方法中明确读取响应所需的关联数据，避免控制器和 JSON 序列化阶段临时访问数据库。
3. 设置 `spring.jpa.open-in-view=false`，运行接口测试、完整 Maven 测试和实际本机启动检查。
4. 如果调整查询方式，要检查是否产生明显的重复查询；没有 SQL 统计前不得声称性能提高。

完成标准：`spring.jpa.open-in-view=false` 生效；商品、广告和订单相关接口没有延迟加载异常；响应字段保持兼容；服务层事务结束前已经准备好响应所需的数据。

## SEC-002：敏感请求头日志

外部依赖探针发现，OSS SDK/Apache HTTP 在 DEBUG 级别会输出完整 `Authorization` 请求头，其中包含 AccessKey ID 和请求签名。AccessKey Secret 未直接输出，但任何凭据材料进入日志都不可接受。

修复要求：

- 轮换本次验证使用的 OSS AccessKey；
- 生产和测试日志配置显式禁止 `org.apache.http.headers`、`org.apache.http.wire` 等敏感网络日志；
- 日志过滤器对 `Authorization`、Cookie、token、签名和 AccessKey 字段做结构化脱敏；
- 添加捕获日志的自动化测试，断言敏感标记和探针凭据均不存在；
- 测试不得把真实凭据写入 fixture、快照或失败消息。

## SEC-009：支付宝 SDK 业务错误日志

## CART-002：商品详情页加入购物车的商品 ID 类型不兼容

CART-001 将购物车添加接口收紧为 JSON 正整数：字符串、小数和布尔值都必须返回 HTTP 400。商品列表使用后端响应中的数字 `product.id`，浏览器已验证可以正常加入购物车；商品详情页则使用路由参数 `route.params.productId`，其运行时类型是字符串，现有 `addToCart(productId.value, quantity)` 会把字符串直接写入 JSON，因此在商品和库存都正常时仍稳定得到“请求参数不完整或格式错误”。

该问题应作为独立的小型兼容修复处理：先写前端边界测试证明合法数字字符串转换为正整数、空值/小数/负数/超范围值拒绝，再让商品详情和商品列表共同调用同一个类型安全的购物车请求入口。浏览器验收必须分别从详情和列表加入商品，并验证非法路由参数不会请求后端。不得放宽后端严格 JSON 解析来迁就错误的前端类型，因为该限制用于避免模糊转换和非法数量绕过。

## ACCT-002：可选手机号为空时注册被错误拒绝

注册页面明确把手机号和邮箱标为可选，但两个输入框的初始值均为空字符串，注册请求会原样提交。`AccountRegistrationDTO.toPO()` 也会把空字符串直接写入账户实体；`AccountServiceImpl.validateAccountUniqueness()` 随后无条件调用 `findByTelephone("")`。只要数据库里已有一个空手机号账户，后续所有不填写手机号的注册请求都会被错误识别为手机号重复。2026-08-17 的真实浏览器回归已经复现 HTTP 409 和“电话号码已存在”提示；填写一个未使用的本地测试手机号后，同一注册流程成功，说明失败不是依赖升级或页面按钮失效。

修复应统一定义可选联系方式的规范形式，而不是只在前端把空字符串改成 `undefined`：注册和资料更新进入服务层时，应把 `null`、空字符串和只含空白字符的手机号、邮箱统一规范为 `null`；只有非空手机号才参与唯一性查询。还需检查数据库中既有空字符串记录，并通过新的 Flyway 迁移或受控数据修正统一为 `NULL`，避免不同入口继续产生两种表示。测试必须使用真实 MySQL 覆盖多个不填手机号的账户均能注册、重复真实手机号仍返回冲突、资料更新清空可选联系方式的语义一致，并用真实浏览器确认不填手机号可以注册和登录。邮箱目前没有唯一性校验，但仍应采用相同的空值规范，避免未来新增约束时重复出现同类问题。

## SEC-014C：开发与构建工具的跨主要版本安全升级

SEC-014A 的正式门槛只针对会进入浏览器运行依赖树的 `npm audit --omit=dev`。重新执行包含开发依赖的完整审计后，仍有 1 个严重、5 个高危、6 个中危，主要涉及 Vitest 2、Vite 5、Rollup 4、旧版自动导入/组件插件及其文件匹配依赖。这些包不进入部署给用户的 JavaScript 运行依赖树，但测试、开发服务器和构建过程会在开发者电脑或未来 CI 上执行，因此不能把“生产严重/高危清零”扩大表述为“整个前端依赖树无安全告警”。

该问题必须作为独立任务处理，因为当前修复建议需要 Vitest、Vite、`@vitejs/plugin-vue`、自动导入或组件插件跨主要版本升级，和已经确认的 SEC-014A 范围冲突。SEC-014C 需要先核对公告是否依赖运行不受信任测试、构建不受信任源码或把开发服务器暴露给外部网络，再制定工具链升级矩阵；不得仅靠 `overrides` 强行把不满足父依赖契约的构建工具拼在一起。

## SEC-015：支付返回过程把登录令牌复制到浏览器存储

当前登录令牌已经放在 HttpOnly Cookie 中，正常页面 JavaScript 无法读取 Cookie 内容；但订单支付页面在跳转支付宝前又把同一令牌复制到 `localStorage.payment_temp_token`，支付宝返回后由路由代码恢复。这使任何能够在商城页面执行的恶意脚本都可能读取令牌，而且 `localStorage` 不会随单个页面关闭立即消失，实际保护弱于 HttpOnly Cookie。

本项不在 SEC-014A 依赖升级中顺手处理。它应与 PAY-002 的服务端可信支付返回页一起实施：删除临时 JWT 的写入、读取和恢复逻辑；支付宝同步返回只提供导航线索，页面必须使用 HttpOnly Cookie 调用后端订单详情或支付状态接口；只有服务端确认订单属于当前用户且状态为 `PAID` 时才显示成功并执行已经明确设计的购物车清理。伪造 `payment_success`、`orderId` 或提前返回都不能改变订单、显示成功或删除购物车数据。

## SEC-004：测试日志中的临时开发口令

默认 Spring Boot 测试上下文会自动生成开发安全口令并以 WARN 写入构建日志。该值不是 `.env`、JWT、OSS 或支付配置，也只对当前临时上下文有效，但凭据类信息仍不应出现在 CI/会话输出。

2026-08-09 Red 阶段在不启动 Spring 的原生日志测试中模拟同一 logger，确认其有效级别继承为 INFO 且占位消息会进入 appender；Green 阶段仅在 `logback-test.xml` 将 `UserDetailsServiceAutoConfiguration` logger 设为 OFF。Green 后目标日志测试 2/2、默认完整测试 31/31 通过，完整输出不再出现生成口令提示。该设置只影响测试，不用于掩盖生产环境的认证配置；生产认证边界后续已由 SEC-001/PR #5 收紧，CSRF 等剩余边界由 SEC-012 跟踪。SEC-004 已完成并转入冷层。

## SEC-003：匿名图片上传

`LoginInterceptor` 当前明确放行 `POST /api/images`，而控制器会使用服务器持有的 OSS 凭据执行上传。任何能访问后端的人都可能借此消耗存储和公网流量，且当前没有可靠的文件大小、实际 MIME 内容或对象命名限制。

兼容性冲突：注册页当前会在账号创建之前调用同一个 `/api/images` 上传可选头像，而 `Account.avatar` 允许为空，登录后的个人中心已提供头像上传与账号更新。推荐移除注册前匿名上传，注册页改为提示登录后设置头像；不得为了保留可选头像而继续公开通用 OSS 写入口。

修复必须先写失败测试，并至少做到：

- 未登录请求不能上传；
- 注册页不再在认证前调用 `/api/images`，且无头像注册仍可成功；
- 根据头像、商品图和广告图的实际业务边界确定普通用户与管理员权限；
- 在控制器和服务边界限制大小、扩展名与实际文件类型；
- object key 由服务端生成，不能信任原始文件名；
- OSS 异常响应和应用日志不得包含凭据、签名或本地文件内容。

2026-08-09 TDD 证据：首轮 9 个目标测试中 8 个按预期失败，证明匿名放行、敏感 logger、原文件名和缺少文件校验等缺陷可复现；实现最小修复后 9/9 通过。第二轮新增用途权限、分类前缀、Endpoint、元数据和空配置测试，12 个目标测试中 6 个按预期失败；实现后 12/12 通过。完整后端测试为 17/17，前端 `vue-tsc && vite build` 成功。

当前实现：注册页移除头像上传并提示登录后在个人主页设置；所有前端调用显式传入图片用途；未登录图片请求业务码 401；普通用户可上传头像，但商品和广告图片要求管理员；服务端生成按用途隔离的 UUID key，并在调用 OSS 前拒绝空文件、超过 10 MiB、声明类型不匹配、签名不支持或不可解码的内容。历史上曾由 ImageIO 在像素数检查前完整解析图片；现已改为先读取图片尺寸并拒绝像素数超限的内容，再执行完整解码。SEC-003 及后续 OSS 修复证据已经进入冷层交付记录。

## FE-002：冷启动首次点击疑似重载

2026-08-10 普通浏览器人工烟雾确认 SEC-011/SEC-001 的日志、普通用户菜单、Cookie、退出和认证来源行为正常，但登录、个人资料、购物车和商品入口出现“第一次点击像刷新，第二次点击才进入目标路由”的体验。现有路由代码没有主动刷新；Live2D 依赖只注册卸载清理和右下角固定画布，也没有调用 `location.reload`。Compose 前端使用 Vite 开发服务器，冷启动日志明确显示依赖重新优化，容器内缓存仍处于 `deps_temp_*`；在依赖已预热后，独立浏览器对登录、个人、商品和购物车的第一次点击均成功，因此当前不能直接归因于按钮或路由守卫。

处理前先获得可重复证据：使用全新的前端匿名 `node_modules` 卷，保留浏览器 Network 日志，记录第一次点击前后的地址、是否出现新的 Document 请求、Vite 是否报告依赖优化后重载，以及相同生产构建预览是否复现。只有证明触发条件后才修改 Vite 预构建、Compose 前端运行方式或页面代码；不得用重复调用 `router.push`、延时跳转或要求用户双击掩盖问题。

前端依赖预热后，独立浏览器对登录、个人、商品和购物车入口均在第一次点击进入目标路由，项目所有者随后在普通浏览器复测也确认现象消失。当前证据更符合 Vite 开发服务器冷启动依赖优化造成的一次性重载体验，不构成 SEC-011/SEC-001 的交付阻塞；由于没有稳定复现和代码修复证据，FE-002 保留为低优先级观察项，不能标记成“代码已修复”。

## FE-003：商品浏览与结算页面控制台错误
