# 安全边界、测试、数据库与前端质量计划

## SEC-001：认证与授权

以下是 SEC-001 开始前的缺陷基线与合并后仍保留的边界，不能把已经修复的条目继续描述成当前缺陷：

- 剩余边界：Spring Security 配置仍是 `anyRequest().permitAll()`，授权依赖 MVC 拦截器和控制器/服务层判断，边界分散；
- 历史缺陷：拦截器曾放行 `/api/orders`、`/api/cart`、`/api/products` 等整个前缀；PR #5 已改为按 HTTP 方法和精确路径判断公开接口；
- 历史缺陷：注册请求曾允许提交 `role`；现已改为服务端固定创建普通用户，资料更新保留数据库中的既有角色；
- 历史缺陷：购物车更新/删除曾未验证条目归属，支付表单曾未验证订单归属；PR #5 已补账户、购物车和支付表单所有权校验及真实 MySQL/MockMvc 测试；
- 历史缺陷：JWT 签名密钥曾硬编码，Cookie 与 JWT 生命周期曾不一致；现已迁移到必填 `JWT_SECRET` 并统一有效期；
- 历史缺陷：`LoginInterceptor` 曾只读取 Cookie，而 `TokenUtil` 和 Axios 还支持 `token` 请求头；现已统一单来源、相同双来源和冲突双来源规则；
- 剩余边界：Spring Security 仍是 `anyRequest().permitAll()`，具体认证和资源权限由 MVC 拦截器、控制器和服务层共同承担；CSRF 仍关闭，由 SEC-012 单独处理；
- 历史前端登录页面会把完整登录响应和账户响应输出到浏览器控制台；登录响应数据包含 token，账户响应包含角色、电话等资料。旧运行归档曾错误写成已删除，本轮已由 SEC-011 修复并建立自动化防回归检查。

SEC-001 当时先写权限矩阵失败测试，再统一 Security/拦截器职责；测试覆盖未登录、普通用户、管理员、资源所有者和跨用户访问，而不是只断言 `validateAdminRole` 被调用。后续 SEC-012 修改认证结构时必须保留这些回归证据。

### 2026-08-10 已确认的 SEC-011/SEC-001 开发基线

项目所有者确认 SEC-011 与 SEC-001 使用同一开发分支 `fix/auth-boundary-and-sensitive-logging`，从 `master@6592fe27` 开始并严格按 SEC-011 → SEC-001 顺序处理。计划合并目标为个人 Fork 的 `master`；实现、测试和独立审查完成前不提交、不推送、不创建 Pull Request。

已确认权限决定：

- 管理员不能替其他用户发起支付；普通用户和管理员都只能为属于自己的 `PENDING` 订单生成支付表单。
- 浏览器暂时保持现有兼容方式，同时发送 HttpOnly Cookie 和精确名称为 `token` 的请求头；单独使用任一来源都允许，两者同时存在时必须相同，值不同或存在多个冲突值时统一拒绝，不能让拦截器和控制器采用不同身份。
- CORS 由反射任意 Origin 改为明确前端来源白名单；认证 Cookie 增加 `SameSite=Lax`。CSRF 本轮仍保持关闭，不把“尚未建立 CSRF token 前端协议”伪装成已经解决；后续由 SEC-012 完成前端 token、公开登录/注册和支付宝 notify 例外的兼容设计与测试。
- JWT 签名密钥迁移为环境变量配置，真实 `.env` 不读取也不修改；测试使用专门的伪密钥。JWT 与 Cookie 使用同一个可配置有效期。
- `PATCH /api/accounts/{username}/points` 当前没有可信业务授权规则，且没有前端调用证据。本轮保持拒绝并由 ACCT-001 单独定义，不能因为移除旧拦截器路径判断而意外允许用户自行设置积分。
- 购物车零数/负数问题由 CART-001 单独跟踪；SEC-001 本轮只处理身份与资源所有权，不能把未测试的数量规则描述成已完成。

建议分层职责：MVC 拦截器只负责精确公开路由和是否登录；`TokenUtil` 集中解析并验证认证来源；控制器和服务负责购物车、订单等具体资源所有权；商品、库存、广告继续保留管理员角色检查；支付宝 notify 是精确公开的外部回调。Spring Security 本轮不大规模改写成另一套 JWT 过滤器，避免形成互相矛盾的双重认证实现。

本轮权限矩阵如下。这里的“公开”只表示不要求商城用户 JWT，不表示可以跳过接口自身的签名、参数或业务校验。

| 请求 | 未登录 | 已登录非所有者 | 资源所有者 | 管理员 | 额外规则 |
|---|---|---|---|---|---|

| `GET /api/products/**` | 允许 | 允许 | 允许 | 允许 | 只放行 GET；同前缀的创建、更新、删除仍需登录且保留管理员校验 |
| `POST /api/orders/notify` | 允许 | 允许 | 允许 | 允许 | 支付宝服务器入口；仍必须通过 RSA2 验签、应用/收款方、金额、状态和事务校验 |

## TEST-002：恢复 Maven 默认测试进程隔离

Surefire 是 Maven 运行 JUnit 测试的组件。它默认会启动独立的 Java 测试进程，使测试使用的内存、系统属性和退出行为与 Maven 主进程隔离。项目曾在这种独立进程中出现原生内存不足，随后使用 `-DforkCount=0` 让测试直接运行在 Maven 主进程中：OSS 安全批次完成时为 52 项，ORD-001 当前完整回归为 79 项。这个替代方式证明了测试内容能通过，但不能永久代替正常的测试进程隔离。

处理顺序：

1. 使用占位 OSS 配置和本机测试数据库/Redis 执行不带 `-DforkCount=0` 的 `mvn test`，保存失败类型、Java 版本、可用内存和测试进程数量；不得记录任何真实凭据值。
2. 区分操作系统可用内存不足、Java 堆设置不合理、重复启动 Spring 上下文或测试并发过高，不能在没有证据时只增加内存参数。
3. 先用最小测试集合复现，再调整 Surefire 或测试上下文复用方式；不能通过跳过测试、移除真实事务测试或把所有测试永久塞进 Maven 主进程来取得绿灯。
4. 最终使用仓库约定的默认命令连续执行两次，确认结果可重复。

完成标准：不添加 `-DforkCount=0` 的 `mvn test` 连续两次通过；默认测试不连接真实支付宝或 OSS；测试报告仍包含全部应执行的单元测试和集成测试；文档记录本机或 CI 所需的最低合理内存和实际使用的 Surefire 设置。

## JPA-001：关闭 Open Session in View 前明确数据读取边界

Open Session in View 是 Spring Boot 默认开启的一种 JPA 行为：HTTP 请求生成响应期间，数据库会话仍保持打开，因此控制器或 JSON 序列化阶段也可能临时读取尚未加载的关联数据。它能暂时掩盖服务层没有完整读取数据的问题，也可能把数据库查询推迟到响应生成阶段。当前商品规格、商品详情图和广告关联使用延迟加载，所以不能直接关闭该选项后假设接口仍然兼容。

处理顺序：

1. 为商品详情、广告详情、订单详情和订单列表接口补充接口级测试，确认响应字段和查询结果。
2. 在 Repository 查询或带事务的服务方法中明确读取响应所需的关联数据，避免控制器和 JSON 序列化阶段临时访问数据库。
3. 设置 `spring.jpa.open-in-view=false`，运行接口测试、完整 Maven 测试和实际本机启动检查。
4. 如果调整查询方式，要检查是否产生明显的重复查询；没有 SQL 统计前不得声称性能提高。

完成标准：`spring.jpa.open-in-view=false` 生效；商品、广告和订单相关接口没有延迟加载异常；响应字段保持兼容；服务层事务结束前已经准备好响应所需的数据。

## FE-002：冷启动首次点击疑似重载

2026-08-10 普通浏览器人工烟雾确认 SEC-011/SEC-001 的日志、普通用户菜单、Cookie、退出和认证来源行为正常，但登录、个人资料、购物车和商品入口出现“第一次点击像刷新，第二次点击才进入目标路由”的体验。现有路由代码没有主动刷新；Live2D 依赖只注册卸载清理和右下角固定画布，也没有调用 `location.reload`。Compose 前端使用 Vite 开发服务器，冷启动日志明确显示依赖重新优化，容器内缓存仍处于 `deps_temp_*`；在依赖已预热后，独立浏览器对登录、个人、商品和购物车的第一次点击均成功，因此当前不能直接归因于按钮或路由守卫。
