# OSS 第一轮评审整改计划

## 背景与目标

OSS-001、OSS-002、SEC-002、SEC-003 和 SEC-004 的第一轮只读评审确认真实生命周期探针、随机对象名、用途隔离、禁止覆盖和已知敏感 HTTP logger 关闭有效，但整体变更暂不批准合并。本计划记录评审缺陷、严格顺序、TDD 证据和第二轮独立审查要求。

本轮只处理评审指出的六类问题，不扩展 AI assistant、交易链路、支付或 Redis 功能，也不提交或推送 Git。

## 严格实施顺序

### 1. SEC-005：注册角色权限提升

Red：服务层测试证明客户端传入 `ADMIN` 当前会被保存为管理员；继续证明普通用户可通过个人资料更新 DTO 把自己的 `role` 改为管理员。接口级契约必须保证两条公开路径都不能授予管理员。

Green：公开注册在服务端强制角色为普通用户，不信任 `AccountVO.role`；个人资料更新忽略客户端 `role`，保留数据库已有角色。不得破坏已有管理员登录或把已有管理员降级。前端注册页移除管理员选择，个人主页角色仅展示或完全移除编辑能力，避免产生误导性契约。

验收：普通注册成功；提交任意大小写管理员角色仍保存普通用户；普通用户更新资料不能提权；已有管理员更新其他资料后仍为管理员；图片 PRODUCT/ADVERTISEMENT 管理权限不能通过注册或资料更新获得。

2026-08-09 证据：准备注册红测时进一步发现资料更新的等价提权路径，并在编码前同步扩展 BACKLOG。新增 3 个服务边界测试，Red 阶段分别得到 `ADMIN`、`ADMIN`、`USER` 三个错误角色结果；Green 阶段注册强制 `USER`、资料更新保留数据库角色，3/3 通过。图片上传相关鉴权组合回归 9/9 通过；前端移除注册角色选择和个人主页角色编辑后 `npm run build` 成功，仍只有 FE-001 已登记的既有构建警告。

### 2. IMG-001：解码前像素限制

Red：构造声明尺寸超过 40,000,000 像素但文件体积很小的合法格式头部，证明当前实现进入完整解码路径或无法在解码前拒绝；补 PNG、JPEG、GIF 正常样本。

Green：使用 `ImageReader`/`ImageInputStream` 在创建完整 `BufferedImage` 前读取宽高并校验正数、乘法溢出和像素上限，然后再执行内容可解码校验。所有 reader、stream 必须关闭，不把原文件名作为可信格式依据。

验收：超限尺寸在 OSS 调用前拒绝；正常三种格式保持兼容；10 MiB 限制不变。

2026-08-09 证据：新增测试先因 `ImageDimensionValidator` 不存在而在 testCompile 阶段准确失败。Green 使用 `ImageReader`/`ImageInputStream` 只读取宽高，reader 与 stream 均在完整解码前关闭；测试用 1×1 PNG 修改 IHDR 为 10,000×5,000 并重算 CRC，文件保持很小但在 OSS 调用前被拒绝。补充服务接入、JPEG 和 GIF 回归后目标测试 10/10 通过。

### 3. RUN-002：Compose 数据库端口

Red：增加不读取或输出秘密的 Compose 配置测试/脚本，证明 backend 必须解析为 `DB_HOST=db`、`DB_PORT=3306`，而宿主机仍可使用映射端口 3307。

Green：在 Compose backend 环境显式覆盖 `DB_PORT=3306`。先完成 `docker compose config --quiet` 和解析级验证；镜像拉取若仍受网络阻塞，保留 RUN-002 的 blocked 状态并明确未完成四容器验收。

2026-08-09 证据：新增 `Test-ComposeConfiguration.ps1`，脚本在内存解析 `docker compose config --format json` 且不回显原始环境。Red 阶段准确失败为 backend DB_PORT 不是 3306；Compose 显式覆盖后脚本输出容器 `db:3306`、宿主机 `127.0.0.1:3307`，`config --quiet` 返回 0。随后 `docker compose build` 超过一分钟没有任何进度输出，按既有 registry 阻塞终止等待；未执行删除、替换容器/镜像/卷，四容器运行验收仍未完成。

### 4. OSS-003：孤儿对象

先设计再写 Red。优先采用两阶段对象状态：上传进入隔离临时前缀，业务保存成功后由后端确认/复制到业务前缀并清理临时对象；或采用权限等价但更简单、可证明不会任意删除已确认业务图片的方案。不得直接把 `oss:DeleteObject` 扩大到整个业务图片前缀。

验收必须覆盖上传后业务失败、超时重试、确认成功、重复确认和清理失败。若本机/面试范围决定采用 Bucket Lifecycle 延迟回收临时前缀，需把具体规则作为无秘密策略模板纳入仓库，并验证应用只返回已确认对象 URL。

2026-08-09 已确认决策：项目所有者选择方案 A。本机和面试阶段暂不实现自动清理未被商品、广告或头像使用的云端图片，完整的两阶段方案保留为长期 P2。应用账户继续没有删除 avatar、product、advertisement 业务图片的权限，避免应用故障或凭据泄露时能够删除真实图片。本轮不为此编写不完整的补偿删除代码，继续处理日志秘密遮挡和阿里云拒绝删除业务图片的安全验证。

### 5. SEC-002：日志兜底脱敏

这里的“日志兜底脱敏”是指：在日志真正输出到控制台或文件之前，把 Authorization、Cookie、Token、签名、AccessKey 等敏感字段的值替换为 `***`。它是对现有“关闭已知危险日志类别”的补充保护，不代替关闭 Apache HTTP 详细请求日志。

Red：向测试 appender 写入只含测试占位值的 Authorization、Cookie、token、签名和 AccessKey 字段，证明当前非关闭 logger 会原样输出。

Green：在生产与测试共享的日志边界实现统一脱敏，已知 headers/wire logger 继续保持 OFF。不得在测试 fixture、快照或失败消息中使用真实凭据。

验收：结构化占位敏感字段被遮蔽；普通日志保持可读；真实 OSS 探针仍无敏感输出。

2026-08-09 真实权限验证新增证据：通用日志正文和异常消息遮挡测试 7/7 通过，但阿里云 SDK 在权限拒绝时仍通过 `com.aliyun.oss` 的 WARN 日志输出完整云端诊断响应。该响应没有 AccessKey 或签名，但包含 Bucket 域名、请求编号、账户内部编号和编码诊断内容。需要新增失败测试证明当前可输出，再关闭 SDK 自己的详细拒绝日志；业务代码仍通过异常类型和错误码判断权限结果。

2026-08-09 修复与复验证据：新增测试准确证明阿里云 SDK 日志原来为 WARN 且诊断字段不会被通用规则遮挡。修复后 SDK 日志关闭，HostId、RequestId 和 EncodedDiagnosticMessage 等字段也加入通用遮挡；相关日志测试 9/9 通过。再次运行真实权限验证时，三个业务目录仍全部被阿里云拒绝，测试 1/1 通过，控制台不再出现云账户诊断详情。

### 6. OSS-004：格式与 RAM 有效权限负测

这里的“RAM 有效权限负测”是指：使用商城运行账户请求一项不应被允许的操作，确认阿里云实际返回权限拒绝。本项目只尝试删除随机生成、从未上传过的文件名，以证明应用不能删除商品、广告和头像目录中的图片；不会对任何现有图片发起删除。

补 PNG、JPEG、GIF 成功测试和声明 MIME 不匹配测试。真实权限负测仅对随机生成、可证明不存在的 avatar/product/advertisement key 发起 DeleteObject；预期云端返回权限拒绝。不得对已有或用户提供的 object key 执行删除。

真实负测必须显式启用、默认 `mvn test` 不运行；失败消息只能包含阶段和脱敏错误类别。执行前确认 RAM 账号无额外组策略或系统策略，执行后无需创建或清理业务对象。

2026-08-09 证据：补充声明为 PNG 但实际为 JPEG 的拒绝测试后，图片服务测试 9/9 通过；安全验证编排的测试先因类不存在而编译失败，实现后本地行为测试 3/3 通过。真实入口 `scripts/Invoke-OssBusinessDeletePermissionProbe.ps1` 使用随机文件名，先确认文件不存在，再分别请求删除 avatar、product、advertisement 目录中的该文件。阿里云三次均返回权限拒绝；首次运行发现 SDK 详细诊断日志并转入 SEC-002 修复，第二次运行 1/1 通过且输出干净。两次运行都没有上传对象，也没有删除任何真实图片。

在增加“直接加载正式日志配置”测试之前，完整后端回归使用本机 MySQL/Redis连接配置和假的 OSS 占位值执行，真实 OSS 验证开关保持关闭，当时的 48/48 测试通过。另一次未读取本机配置的尝试因默认数据库主机名 `db` 只适用于 Compose 网络而产生 1 个 Spring 上下文连接错误；这次环境错误没有作为通过证据。增加正式配置测试后当时更新为 49/49；第二轮审查又增加生命周期安全测试后，当时更新为 50/50。

## 第二轮独立评审

全部整改与本地验证完成后，主代理必须启动一个 `fork_turns="none"` 的冷启动 subagent，只提供项目路径、AGENTS.md、评审范围和验收标准，不提供实现过程结论。subagent 必须独立读取 diff、代码、测试和文档，并按优先级报告问题。主代理再复核其证据，不能把 subagent 的“通过”直接当作合并授权。

第二轮评审通过后仍不得自动提交、推送或 merge；必须等待项目所有者明确授权。

### 2026-08-09 第二轮审查结果与处理顺序

不继承本会话实现过程的独立审查发现以下问题，主代理复核后接受：

1. Compose 将没有密码的 Redis 通过 `6379:6379` 发布到宿主机所有网络接口。由于本机后端需要直连 Compose Redis，本轮采用 `127.0.0.1:6379:6379`，只允许本机访问，并为 Compose 配置测试增加明确断言。
2. 旧生命周期验证在上传失败后仍无条件删除 `_validation` 下的随机文件名。虽然不会影响业务图片，但应先确认随机名称不存在，并区分“确认没有创建”和“请求可能已经到达云端但客户端没有收到响应”两类失败，避免删除先前对象。
3. 审查时 BACKLOG 同时保留历史 31/31、48/48 和当时的当前结果 49/49，未清楚说明对应阶段，需明确命令和代码状态，避免把旧数字误当成最终结果。
4. assistant 废弃决策已经进入冷层，但状态 `archived` 不在文档规则允许的 `completed/superseded/cancelled` 中，应改为 `cancelled`。

处理顺序为 SEC-006 → OSS-005 → DOC-001。完成后再次运行 Compose 配置检查、后端完整测试、文档 Frontmatter 检查和 `git diff --check`；然后对修复结果做针对性复核，不得直接沿用修复前的审查结论。

2026-08-09 修复结果：Redis 端口改为 `127.0.0.1:6379:6379`，Compose 配置测试先失败后通过；生命周期验证增加上传前 404 检查，上传异常不再删除未确认创建的文件，目标测试 5/5、相关工具测试 16/16、真实生命周期验证 1/1 通过；文档最终测试数量统一为 50/50，历史数字标明阶段，冷层 assistant 废弃决策状态改为 `cancelled`。等待针对性复核。

2026-08-10 修复后复核：独立审查确认上述四项当前行为正确，但发现 Compose 测试只读取 Redis 第一条端口映射。若保留 `127.0.0.1:6379:6379` 并追加另一条对所有网络接口开放的映射，旧测试仍可能通过。测试必须改为要求 Redis 恰好只有一条端口映射，再检查该映射的绑定地址和端口；通过临时加入第二条不安全映射证明测试能够失败，恢复安全配置后再证明通过。另补充失败消息不包含随机 OSS 文件名的直接断言。

2026-08-10 最终补强证据：Compose 测试先增加“Redis 恰好只有一条宿主机映射”断言，再临时追加第二条 `6380:6379`，测试准确失败；通过补丁移除临时映射后，配置测试和 `docker compose config --quiet` 均通过，容器未被启动或替换。生命周期失败消息增加不包含随机对象名的直接断言，目标测试 5/5 通过。最终独立复核前的完整后端测试使用本机 MySQL/Redis和假的 OSS 值执行，真实 OSS 开关关闭，当时 50/50 通过。

### 2026-08-10 最终独立复核新增问题

最终补强后，由不继承实现过程的新 subagent 进行只读复核，发现以下问题，主开发代理复核代码路径后接受并同步登记 BACKLOG：

1. SEC-007：公开注册使用的 `AccountVO.toPO()` 会把客户端 `id` 写入自增主键实体，注册服务只固定了角色，没有清空 ID。对已有 ID 调用 JPA `save` 可能更新原账户。必须先用真实数据库测试预置账户并复现，再使用不包含服务端字段的注册输入和服务层防御性清空完成修复。
2. OSS-006：生命周期探针只有在上传方法正常返回后才清理。若 OSS 已接受写入但客户端在收到响应前异常，安全策略要求不能盲删，但失败结果必须明确报告“可能残留”，不能显示为没有清理问题。测试和错误消息仍不得包含对象名或云端配置。
3. DOC-002：运行计划仍把 Compose 只覆盖 `DB_HOST` 写成当前缺陷，但实际 Compose 和配置测试已经固定 `DB_PORT=3306`。文档应改为历史缺陷已修复，并保留完整四容器运行尚未验收的真实阻塞。

处理顺序为 SEC-007 → OSS-006 → DOC-002。完成后重新执行目标测试、后端完整测试、前端构建、Compose 配置检查、文档检查和 `git diff --check`，再启动新的针对性独立复核。

2026-08-10 修复与验证证据：

- SEC-007：真实 MySQL 接口测试先预置账户，再向公开注册接口提交相同 ID。Red 阶段准确失败为原账户用户名被改成攻击者用户名；公开注册改用不包含 `id`、`role`、`points` 的 `AccountRegistrationDTO`，服务层保存前再次清空 ID。Green 后目标测试 1/1、包含原角色安全测试的相关测试 4/4 通过，测试事务已经回滚。
- OSS-006：在上传异常测试中先断言失败结果必须包含 `residuePossible=true`，Red 阶段因消息缺少该状态而失败；Green 后上传结果不确定会提示可能残留，删除失败会同时标记清理失败和可能残留，生命周期测试 5/5 通过，消息继续不包含对象名。
- DOC-002：运行计划已把 `DB_HOST`/`DB_PORT` 问题改成历史缺陷已修复，当前阻塞只保留镜像拉取和四容器运行尚未完整验收。
- OSS-007 修复前的完整验证：`mvn compile` 成功；使用本机 MySQL/Redis、假的 OSS 值、关闭两个真实探针，并明确使用 `-DforkCount=0` 的后端测试当时为 51/51；`npm run build` 成功，只有 FE-001 已登记的既有警告；Compose 配置检查通过，端点为容器 `db:3306`、宿主机 MySQL `127.0.0.1:3307`、宿主机 Redis `127.0.0.1:6379`。

## 2026-08-10 针对性独立复核新增问题

针对 SEC-007、OSS-006 和 DOC-002 的冷启动只读复核确认三项原目标已经实现，但发现新的 OSS-007：上传已经正常返回后，如果匿名读取验证抛异常或返回非 200，探针会调用删除；然而该失败路径不会继续执行删除后的 404 检查，因此无法证明验证对象已经不存在。当前失败消息仍使用默认 `residuePossible=false`，会给操作者不准确的风险提示。

处理顺序严格遵循 TDD：先分别覆盖“匿名读取抛异常”和“匿名读取返回非 200”两个分支，断言删除仍被调用，同时失败消息必须为 `cleanupFailed=false, residuePossible=true` 且不包含对象名；确认测试在当前实现上准确失败后，再把这两个没有删除后验证证据的分支改为保守报告可能残留。修复不得尝试删除未确认创建的对象，不得扩大业务图片删除权限，也不得在错误消息中加入对象名、URL、Bucket、Endpoint、异常原文或凭据。

2026-08-10 实施证据：新增两个断言后，目标测试 6 项中 2 项准确失败，均因为消息仍是 `residuePossible=false`；只修改匿名读取异常和非 200 两个分支后，目标测试 6/6 通过。完整测试第一次因测试进程沿用非本机数据库地址而出现 `No database selected`，不能作为通过证据；按 AGENTS.md 约定显式使用宿主机 MySQL `127.0.0.1:3307` 后，真实数据库注册测试 1/1、完整后端测试 52/52 通过。测试使用假的 OSS 参数并关闭真实探针，没有访问真实 OSS。

2026-08-10 最终冷启动只读复核没有发现阻塞项或新的 P0/P1/P2/P3 回归。复核确认匿名读取异常和非 200 两条路径会继续调用删除，但在没有删除后 404 证据时准确报告 `cleanupFailed=false, residuePossible=true`；上传未确认时仍不盲删，删除调用失败与删除后验证失败也分别使用准确状态。失败消息没有包含对象名、URL、Bucket、Endpoint、异常原文或凭据。复核独立汇总默认 Surefire 报告为 14 个测试类、52 项全部通过，两个较早的显式 `*IT` 不计入默认测试。
