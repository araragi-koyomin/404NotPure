# 订单、库存、支付与缓存一致性改造计划

## 目标与边界

在不破坏现有 `/api/cart/checkout`、`/api/orders/{orderId}/pay`、`/api/orders/notify` 和前端字段的前提下，让交易链路具备可由代码与测试证明的事务一致性、库存并发安全、支付幂等和 Cache-Aside 行为。

不引入微服务、消息队列或复杂分布式架构；已废弃的 assistant 完全排除在维护、测试和验收范围外；不虚构并发或性能数据。实现继续基于 Spring Boot 2.7.6、Java 17、JPA、MySQL 8 和 Redis 6。

## 已完成：ORD-001 订单与库存

ORD-001 已于 2026-08-10 通过 [PR #2](https://github.com/araragi-koyomin/404NotPure/pull/2) squash merge 进入 `master`。最终设计、TDD 失败与通过证据、验证命令、独立审查结果和剩余风险统一保存在[交付归档](../archive/2026-08-10-order-inventory-consistency-delivery.md)。下面保留实现约束，供仍在进行的支付、幂等和数据库迁移任务理解库存冻结语义；ORD-001 已不再是活跃工作项。

2026-08-10 实现选择：采用 MySQL 带库存条件的原子更新，不使用悲观锁或 Redis 分布式锁。单个商品通过一条 `UPDATE` 同时执行 `amount -= quantity`、`frozen += quantity`，并要求更新前 `amount >= quantity`。更新语句通过同表左连接确认该商品不存在第二条库存记录，只有唯一库存行才能更新。受影响行数为 1 才表示成功；0 行时再统计该商品的库存记录数，多于 1 行按数据异常回滚，0 或 1 行按库存缺失或不足处理；大于 1 的返回值仍作为防御性数据异常处理。多商品请求先汇总重复商品并按商品 ID 排序，在同一数据库事务中逐项更新；任意一项失败时，前面的库存更新、订单和订单项都不得提交。

选择原因：库存冻结规则只依赖可用数量，适合由一条 SQL 原子完成检查和修改；MySQL 是库存最终数据来源，引入 Redis 锁会增加锁与数据库事务不同步的问题。ORD-001 当时的本机测试数据库为商品 0 行、库存 0 行，因此先对异常的多行更新做失败保护；后来 DB-001B 已通过 Flyway V3 从数据库层增加商品库存唯一约束和外键。

必须实现：

- `OrderServiceImpl.addOrder` 建立覆盖用户校验、商品读取、库存冻结、订单和订单项保存的事务边界；
- 购买数量在 Controller Bean Validation 和服务层边界均校验为正整数；
- 同一请求重复商品先聚合或以等价方式按总量校验；
- 使用已确认的 MySQL 条件原子更新冻结库存，并严格检查受影响行数；
- 并发成功冻结量不得超过可用库存；
- 库存不足时不得创建订单，中途异常时库存、订单和订单项全部回滚；
- 低成本可行时增加重复请求幂等键，但不得用进程内 Map 冒充跨进程幂等。

本轮幂等范围说明：当前 `/api/cart/checkout` 请求没有幂等键，订单表也没有可用于请求去重的唯一字段。可靠实现需要同时定义客户端重试协议、数据库唯一约束和失败重试语义，不属于无需迁移即可完成的低成本修改，因此不在 ORD-001 中仓促加入。该风险已登记为 ORD-002；在其完成前，不能声称“重复点击结算只会创建一个订单”。

TDD 顺序：

1. 非法数量失败测试；
2. 正常下单状态与金额测试；
3. 库存不足且订单不存在测试；
4. 保存中途异常后的事务回滚集成测试；
5. 两个以上事务并发争用库存的真实 MySQL 测试；
6. 最小实现与重构。

### ORD-001 TDD 与验证证据

Red 阶段确认了以下真实缺陷：

- 服务层 8 个非法请求测试原本预期业务码 `400`，实际先访问用户数据并返回“用户不存在”，说明服务层没有先校验订单请求；

- 16 个线程争抢 1 件库存时，旧实现出现 16 个成功订单，证明“先读库存、再保存实体”不能阻止并发超卖。

## ORD-002：结算请求幂等

### 目标、接口与数据约束

ORD-002 于 2026-08-16 完成需求确认，开发分支为 `codex/order-checkout-idempotency`，起点是个人 `master@ea79efdc`。这里的“幂等”是指：同一用户因为重复点击、页面刷新、网络超时后手工重试，重复提交同一次结算请求时，系统只创建一个订单、只冻结一次库存，并返回第一次创建的订单；它不表示不同结算意图会被错误合并。

- `POST /api/cart/checkout` 必须携带 `Idempotency-Key` 请求头。值必须是小写标准 UUID，例如 `123e4567-e89b-12d3-a456-426614174000`；缺失、大小写不规范或格式错误返回实际 HTTP 400。
- 同一用户和同一幂等键永久绑定一个订单。相同业务请求重放时沿用现有成功响应体，并增加 `Idempotent-Replay: true` 响应头；订单后来变为 `PAID`、`CANCELLED` 或 `CLOSED` 时仍返回该订单，不再创建新订单。
- 同一用户用同一键提交不同业务内容时返回实际 HTTP 409，同时保持项目统一的 `Response<T>` 响应结构。不同用户可以使用相同 UUID；同一用户使用不同 UUID 时仍代表两次独立结算，只要库存足够就允许创建两个订单。
- 订单表新增可空的 `idempotency_key` 和 `request_fingerprint`。两列必须同时为空或同时非空；历史 V1～V6 订单保持为空。`idempotency_key` 使用 36 字符 ASCII、区分大小写排序规则，并建立 `(user_id, idempotency_key)` 唯一约束；`request_fingerprint` 保存 64 字符 SHA-256 十六进制摘要。新增结构只能放在 Flyway V7，不能改写已经应用的 V1～V6。
- 新应用创建的订单必须同时写入这两个字段。服务接口不再保留不带幂等键的 `addOrder(userId, dto)` 重载，避免内部调用无意绕过协议。

### 请求内容标准化与支付方式边界

后端是请求是否相同的最终判断者。先验证数量、合并重复商品、按商品 ID 排序，再把支付方式规范化，形成带版本的稳定文本，例如 `v1|paymentMethod=Alipay|items=1:2,2:1`，最后计算 SHA-256。指纹只表示用户提交的业务意图：包含支付方式、商品 ID 和合并后的数量；不包含用户 ID、商品标题、价格、订单状态、Token 或幂等键。用户身份已经位于数据库唯一键的另一列，商品价格始终由服务端在真正创建订单时读取。

本阶段只支持支付宝，但增加最小的 `PaymentMethod` 枚举和 `PaymentMethodResolver`。输入中的前后空格和大小写差异统一规范为现有响应兼容值 `Alipay`；未知支付方式返回 HTTP 400。这只是消除散落字符串并为以后增加渠道留出清晰入口，不改造支付宝网关，不实现微信支付，也不建立完整多渠道策略。

### 数据库并发与事务设计

幂等正确性由 MySQL 唯一约束保证，而不是 Java 进程内 Map、Redis 分布式锁或前端按钮禁用。事务工作组件先保存并立即刷新一条已经包含幂等键、指纹、金额和状态的完整订单，以争取 `(user_id, idempotency_key)`；取得唯一键后，继续在同一事务中使用 ORD-001 的条件原子更新冻结库存并保存订单项。

- 第一个请求提交后，等待相同唯一键的请求查询并返回现有订单，不再次冻结库存。
- 第一个请求回滚后，它插入的订单和幂等键一起消失；等待请求可以接管并创建订单，不留下永久占用的失败键。
- 唯一约束冲突必须在失败事务完全退出后，只针对命名约束 `uk_orders_user_idempotency_key` 查询现有订单并比较指纹；其他完整性错误不能伪装成幂等重放。
- 同键同请求返回现有订单；同键不同指纹返回 HTTP 409。实际数据库锁等待或事务超时翻译为 HTTP 503，客户端可以继续使用同一键手工重试。本任务不修改 MySQL 全局锁等待配置，也不在前端自动重试。
- 指标 `tomatomall.order.checkout.requests` 只使用固定结果标签 `created`、`replayed`、`conflict`、`timeout`、`failed`，不得包含用户、订单、商品、幂等键或 Token。

### 前端重试状态

前端为一次结算意图生成一个 UUID，并保存“稳定请求标识 + UUID”；刷新页面、网络错误、HTTP 503 或后端 5xx 后，用户对未修改请求手工重试时继续使用同一键。商品、数量或支付方式发生改变时生成新键。HTTP 409 会清除旧键并显示冲突，不自动再次提交；前端校验失败或库存不足也不自动重试。

订单创建和支付表单生成必须成为两个可恢复阶段：尚无 `orderId` 时才调用结算；一旦成功拿到 `orderId` 就持久化它，后续即使支付宝表单接口失败或页面刷新，也只重试 `/api/orders/{orderId}/pay`，不能再次创建订单。支付成功后的购物车清理和同步返回页可信状态仍由 PAY-002 处理。

只为纯前端幂等状态模块引入 Vitest，不在本任务引入 Playwright 或 Cypress。页面人工验收覆盖正常结算、刷新后状态恢复和支付表单失败后的单独重试；并发、数据库回滚和冲突主要由自动化测试完成。

## ORD-003：取消或超时关闭待支付订单

当前订单只支持 `PENDING -> PAID`。用户创建订单后如果不付款，可用库存已经减少而冻结库存会长期保留，因此需要独立的订单取消和超时关闭任务。本项不与 PAY-001 回调修复混在同一分支，避免同时改动已经完成审查的支付事务。

设计前必须明确：

- 手动取消只允许订单所有者操作，管理员是否可以关闭订单需要单独定义；权限规则与 SEC-001 的订单所有权规则保持一致；
- 只有 `PENDING` 可以进入取消或关闭状态；`PAID` 不能直接取消，退款属于未来独立支付任务；
- 取消或关闭时执行 `amount += quantity`、`frozen -= quantity`，订单状态和所有商品库存恢复必须处于同一数据库事务；
- 支付通知与取消同时到达时，数据库条件更新只能允许其中一个状态方向成功；失败的一方读取最新状态后按幂等或非法状态处理；
- 重复取消、重复超时处理不能重复恢复库存；
- 超时依据使用服务端创建时间和明确的超时时长，不能信任浏览器时间。第一版可使用受控的定时扫描或显式关闭入口，不引入消息队列。

TDD 顺序：订单所有权、正常取消恢复库存、非法状态、重复取消、多商品中途异常回滚、支付与取消并发、超时边界。库存恢复和并发状态竞争必须由真实 MySQL 测试证明。

### 2026-08-16 启动审计与待确认规则

ORD-003 已从个人 `master@b0a098f0` 创建开发分支 `codex/order-cancellation-timeout`。现有代码已经提供 `PENDING -> PAID` 的数据库条件更新，支付成功后只减少冻结库存；下单时则通过数据库条件原子更新同时减少可用库存并增加冻结库存。取消需要新增相反的单条库存更新，即在冻结数量足够时同时执行 `amount += quantity`、`frozen -= quantity`，并让订单状态竞争和全部库存恢复位于同一事务。该方向已经能够从代码确认，不需要重新选择锁方案。

项目所有者已经确认以下规则：

1. 手动取消接口为 `POST /api/orders/{orderId}/cancel`，只有订单所有者可以调用；管理员不能代替其他用户取消；
2. 状态新增 `CANCELLED` 和 `CLOSED`。到期前手动取消进入 `CANCELLED`，达到或超过到期时刻后进入 `CLOSED`；`PAID`、`CANCELLED`、`CLOSED` 都是最终状态；
3. 待支付期限默认 30 分钟，正常应用默认启用自动关闭；每 60 秒扫描一次，每次最多处理 100 个过期订单。时间、扫描间隔、批量上限和开关都通过配置提供；
4. 重复取消 `CANCELLED` 或 `CLOSED` 订单返回幂等成功且不再次修改库存；取消 `PAID` 订单返回业务冲突；
5. 取消或关闭使用数据库条件更新决定唯一处理者，并在同一事务中按商品 ID 顺序执行 `amount += quantity`、`frozen -= quantity`。任一商品失败时订单状态和此前库存更新全部回滚；
6. 支付、手动取消和自动关闭并发时只能有一个 `PENDING` 来源状态更新成功。多个后端实例可以同时扫描，不使用进程内 Map、Redis 锁或消息队列；
7. V6 增加 `cancelled_time`、`closed_time`、`(status, create_time, order_id)` 索引和合法状态检查约束。未知历史状态不自动修正；迁移前只读检查需报告状态、过期订单、异常订单项和冻结库存缺口；
8. 历史 `PENDING` 订单同样使用 30 分钟规则；迁移只改变结构，实际关闭由独立事务业务服务完成。一个异常订单失败时继续处理同批其他订单，并记录不含敏感信息的失败指标；
9. 支付表单使用订单统一到期时刻的剩余有效期，不能在每次生成表单时重新获得 30 分钟。到期后用户请求支付表单时同步尝试关闭；支付宝签名成功通知仍按数据库状态竞争，因为付款可能发生在期限内而通知稍晚到达；
10. 本轮不修改购物车，也不增加依赖订单列表/详情的前端取消按钮；只把结算前实际用于返回的旧“取消订单”文案改为“返回购物车”或“取消结算”。

TDD 顺序细化为：V6 空库/旧库迁移与异常数据拒绝；匿名、跨用户和管理员权限；正常取消与多商品恢复；重复取消和非法状态；后续商品恢复失败时完整回滚；支付与取消并发；支付与自动关闭并发；两个扫描器重复处理；到期前、到期时和到期后的确定性时间边界；历史订单和单个失败不阻塞同批任务；支付表单剩余有效期。

已确认的非目标：不实现退款、支付失败、消息队列、分布式事务、支付成功后的购物车清理或完整订单中心；不维护已经废弃的 AI assistant。已经打开的支付宝页面与本地取消之间仍可能发生晚付款，本轮不调用支付宝交易关闭接口；该外部一致性风险由 PAY-004 独立跟踪，若项目接收真实资金则必须升级为上线阻塞项。

### ORD-003 当前实现与验证证据

V6 使用单条 MySQL `ALTER TABLE` 同时增加 `cancelled_time`、`closed_time`、`(status, create_time, order_id)` 索引和四状态检查约束。由于现有表的 MySQL 排序规则默认不区分大小写，约束使用 `CAST(status AS BINARY)` 强制精确匹配。真实临时库测试证明空库完整迁移、合法旧订单不改写，`UNKNOWN`、`pending`、`Paid` 等旧状态会阻止升级且不留下半套字段或索引；既有支付、库存和购物车迁移测试也已更新为继续执行到 V6，并由 Hibernate 对完整实体结构执行 `validate`。

## CACHE-001：Redis Cache-Aside

当前实际 key 为 `advertisement:product:{productId}`，TTL 随机 1800～3599 秒。这不是错误设计：广告创建/更新会提前缓存更可能被访问的热门商品详情。CACHE-001 要解决的是这份广告预热缓存后来同时承担通用商品详情读取后，回填、失效和类型边界仍不完整。改造必须保留广告商品预热，并保持广告位和商品详情前端行为兼容：

- 集中定义稳定 key；若泛化为 `product:detail:v1:{productId}` 等通用商品详情 key，必须把它描述为职责扩展而非旧设计错误，并让广告预热、商品读取和全部失效入口同批切换或提供兼容读取；
- 商品详情缓存未命中时查库并回填；
- 保留随机 TTL，测试只断言范围；
- 以短 TTL 空值标记或等价方案防缓存穿透；
- 商品更新、删除提交成功后失效缓存；
- 广告更新更换商品时同时失效旧商品 key；
- `AdvertisementsServiceImpl` 和 `ProductServiceImpl` 使用 `RedisTemplate<String, Object>`，不再使用没有泛型参数的原始类型；
- 缓存读取先检查对象实际类型，再转换为 `ProductDTO`。遇到旧数据、错误类型或无法反序列化的数据时，应删除该缓存并从数据库恢复，不能直接强制转换导致商品接口失败；
- 当前项目通过 `RedisTemplate` 使用 Redis，没有定义 Spring Data Redis Repository。应在上下文测试证明 JPA Repository 仍能正常加载后，明确关闭 Redis Repository 自动扫描，避免每次启动进行无意义的 Repository 类型判断；
- `mvn compile` 不再出现由原始 RedisTemplate 引起的 unchecked 类型警告，应用启动不再出现未使用 Redis Repository 扫描产生的提示；
- 缓存故障不得破坏数据库主链路的正确性；
- 不声称没有测量依据的性能提升。

TDD 顺序：缓存命中、未命中回填、数据库不存在空值、错误缓存类型恢复、更新失效、删除失效、广告换品、Redis 异常降级、Spring 上下文中的 JPA/Redis Repository 边界。真实 Redis 测试还要验证序列化后的类型、TTL 范围和失效行为，不能只用 Mock 证明方法被调用。

2026-08-11 当前分支实现与验证：统一切换到 `product:detail:v1:{productId}`，由 `ProductDetailCache` 集中管理读取、写入、随机 TTL、短期不存在标记、类型检查和事务提交后操作；广告创建与更新继续提前缓存关联商品，因此原有热门商品预热行为被保留。商品详情未命中时，使用 MySQL 商品行悲观写锁读取商品、规格和详情图，并在释放行锁前完成回填；商品更新、删除也先取得同一商品行锁，避免更新提交并删除缓存后，较早读取的旧详情又被写回。这个锁只用于缓存未命中和商品后台修改，不改变 ORD-001 的条件原子库存更新，缓存命中仍不访问数据库。商品不存在时写入 60～119 秒标记，正常商品写入 1800～3599 秒；商品创建提交后删除同 ID 的旧标记。本机 MySQL 8 并发测试还证明：在当前默认 `REPEATABLE READ`（可重复读）隔离级别下，缺失查询持有的间隙锁会让同 ID 创建等待，查询事务结束后创建提交并删除旧标记。如果未来改为 `READ COMMITTED`（读已提交）或更换数据库，必须重新验证这一不存在行的并发顺序，不能直接沿用本结论。

广告创建或换品提交后不再写事务中捕获的旧 DTO，而是通过独立新事务重新锁定并读取最新商品，再在释放锁前预热；广告换品回滚时旧缓存保留且新商品不预热。商品更新、删除和广告删除/换出旧商品只在数据库事务成功提交后删除缓存，事务回滚测试证明数据库和缓存都保持旧值。Redis 读取、写入或删除失败会记录不含 key、值和连接配置的固定警告并回退到 MySQL 主链路。Cache-Aside 仍不是 MySQL 与 Redis 的强一致协议：如果事务提交后的 Redis 删除本身失败，旧缓存可能存活到原 TTL；本轮不引入消息队列或可靠事件系统，也不宣称强一致或未经测量的性能收益。

Red 阶段先运行真实集成测试，8 项中出现 1 个失败和 7 个错误：未命中不会回填、商品不存在由 `Optional.get()` 抛出错误异常，以及商品规格/详情图在数据库会话关闭后转换导致 `LazyInitializationException`。缓存组件测试最初因 `ProductDetailCache` 尚不存在产生 19 个编译错误；主开发自查新增的损坏缓存用例又先准确失败，证明旧实现只回退数据库却没有删除无法反序列化的缓存。首轮独立审查后新增 16 项真实集成测试，其中 3 项准确失败，分别证明商品旧快照回填可覆盖更新失效、广告旧快照预热可覆盖更新失效，以及商品创建后旧的不存在标记没有被清理。

修复后缓存组件单元测试 8/8，真实 MySQL 8 + Redis 6 集成测试 17/17，新增带线程启动信号和最终状态断言的双线程测试，证明详情回填和广告预热会与商品更新按同一行锁排序，并验证缺失查询与同 ID 创建的间隙锁顺序、负缓存实际命中、商品创建清理负缓存、广告换品回滚和真实 TTL 读取容差。最终执行 `mvn clean test`，先删除旧 Surefire 报告再完整运行，干净默认回归为 28 个测试类、172/172；报告目录不含真实 OSS/支付宝 `*IT` 外部探针。所有真实测试只清理本测试记录的商品、广告和缓存 key，没有清空数据库或 Redis。
