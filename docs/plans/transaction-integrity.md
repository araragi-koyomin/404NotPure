# 订单、库存、支付与缓存一致性改造计划

## 目标与边界

在不破坏现有 `/api/cart/checkout`、`/api/orders/{orderId}/pay`、`/api/orders/notify` 和前端字段的前提下，让交易链路具备可由代码与测试证明的事务一致性、库存并发安全、支付幂等和 Cache-Aside 行为。

不引入微服务、消息队列或复杂分布式架构；已废弃的 assistant 完全排除在维护、测试和验收范围外；不虚构并发或性能数据。实现继续基于 Spring Boot 2.7.6、Java 17、JPA、MySQL 8 和 Redis 6。

## 已完成：ORD-001 订单与库存

ORD-001 已于 2026-08-10 通过 [PR #2](https://github.com/araragi-koyomin/404NotPure/pull/2) squash merge 进入 `master`。最终设计、TDD 失败与通过证据、验证命令、独立审查结果和剩余风险统一保存在[交付归档](../archive/2026-08-10-order-inventory-consistency-delivery.md)。下面保留实现约束，供仍在进行的支付、幂等和数据库迁移任务理解库存冻结语义；ORD-001 已不再是活跃工作项。

2026-08-10 实现选择：采用 MySQL 带库存条件的原子更新，不使用悲观锁或 Redis 分布式锁。单个商品通过一条 `UPDATE` 同时执行 `amount -= quantity`、`frozen += quantity`，并要求更新前 `amount >= quantity`。更新语句通过同表左连接确认该商品不存在第二条库存记录，只有唯一库存行才能更新。受影响行数为 1 才表示成功；0 行时再统计该商品的库存记录数，多于 1 行按数据异常回滚，0 或 1 行按库存缺失或不足处理；大于 1 的返回值仍作为防御性数据异常处理。多商品请求先汇总重复商品并按商品 ID 排序，在同一数据库事务中逐项更新；任意一项失败时，前面的库存更新、订单和订单项都不得提交。

选择原因：库存冻结规则只依赖可用数量，适合由一条 SQL 原子完成检查和修改；MySQL 是库存最终数据来源，引入 Redis 锁会增加锁与数据库事务不同步的问题。当前本机测试数据库检查结果为商品 0 行、库存 0 行，不存在需要先处理的重复或负库存数据；数据库唯一约束仍由 DB-001 后续通过版本化迁移完成，本轮先对异常的多行更新做失败保护。

必须实现：

- `OrderServiceImpl.addOrder` 建立覆盖用户校验、商品读取、库存冻结、订单和订单项保存的事务边界；
- 购买数量在 Controller Bean Validation 和服务层边界均校验为正整数；
- 同一请求重复商品先聚合或以等价方式按总量校验；
- 使用已确认的 MySQL 条件原子更新冻结库存，并严格检查受影响行数；
- 并发成功冻结量不得超过可用库存；
- 库存不足时不得创建订单，中途异常时库存、订单和订单项全部回滚；
- 低成本可行时增加重复请求幂等键，但不得用进程内 Map 冒充跨进程幂等。

本轮幂等范围说明：当前 `/api/cart/checkout` 请求没有幂等键，订单表也没有可用于请求去重的唯一字段。可靠实现需要同时定义客户端重试协议、数据库唯一约束和失败重试语义，不属于无需迁移即可完成的低成本修改，因此不在 ORD-001 中仓促加入。该风险已登记为 ORD-002；在其完成前，不能声称“重复点击结算只会创建一个订单”。

TDD 顺序：

1. 非法数量失败测试；
2. 正常下单状态与金额测试；
3. 库存不足且订单不存在测试；
4. 保存中途异常后的事务回滚集成测试；
5. 两个以上事务并发争用库存的真实 MySQL 测试；
6. 最小实现与重构。

### ORD-001 TDD 与验证证据

Red 阶段确认了以下真实缺陷：

- 服务层 8 个非法请求测试原本预期业务码 `400`，实际先访问用户数据并返回“用户不存在”，说明服务层没有先校验订单请求；
- 控制器非法请求最初返回 HTTP 200，说明 DTO 上的约束没有通过 `@Valid` 生效；
- 同一商品在请求中出现两次时创建了两条订单项，没有按总数量统一校验；
- 第二个商品库存不足或订单保存抛出异常时，第一个商品已经发生的库存变更没有回滚；
- 16 个线程争抢 1 件库存时，旧实现出现 16 个成功订单，证明“先读库存、再保存实体”不能阻止并发超卖。

Green 阶段实现并验证：

- `OrderServiceImpl.addOrder` 使用数据库事务覆盖用户、商品、库存冻结、订单和订单项保存；
- Controller 与服务层同时拒绝空订单、空商品、空商品 ID、空数量、零数量、负数量和空支付方式；空请求体、JSON `null`、损坏 JSON 和 Bean Validation 参数错误都保持 HTTP 400 和 `Response {code,msg,data}` 包装；
- 重复商品按商品 ID 汇总并排序，数量相加发生整数溢出时拒绝请求；
- `StockPileRepository` 用一条条件更新同时减少可用库存并增加冻结库存；更新 0 行按库存不足处理，更新多行按库存数据异常处理，异常会回滚整个订单事务；
- 真实 MySQL 测试覆盖正常下单、重复商品汇总、库存不足、库存记录缺失、两条都充足的重复库存、仅一条充足的重复库存、订单保存异常回滚和 16 线程并发争抢；
- ORD-001 定向测试 27/27 通过；后端全量测试 79/79 通过；修正重复库存 SQL 后，并发测试另外连续运行 3 次均通过；`mvn compile` 通过。

测试期间发现 `.env` 的数据库主机值带有行内说明文字，简单加载脚本会把说明文字当成配置值。本轮验证脚本已在内存中剥离行内说明；没有修改或提交 `.env`。默认测试仍使用 `-DforkCount=0`，对应的测试进程隔离问题继续由 TEST-002 跟踪。

## PAY-001：支付宝回调

2026-08-10 已确认实施顺序：PAY-001 是下一项业务主目标，但在修改支付状态逻辑前，先完成 DB-001A，为独立支付完成时间和支付宝交易号建立最小版本化迁移路径。实际 schema 检查确认 `orders`、`stockpile` 和 `payment_info` 都是空表，`PaymentInfo` 没有 Repository、外键或业务接入，因此支付结果最终直接保存在 `Orders.paidTime` 和唯一的 `Orders.alipayTradeNo` 中，不继续扩展遗留 `PaymentInfo`。DB-001A 同时建立当前完整 schema 的 V1 基线和支付字段 V2，并把 Hibernate 从自动更新改为只验证；库存商品唯一约束和历史重复数据处理仍由 DB-001 跟踪。

必须实现：

- 保留支付宝异步回调签名校验；
- 验签后继续确认通知的 `app_id` 和收款方 `seller_id` 与本项目配置一致；配置缺失或不匹配时返回 `fail`；
- 校验 `out_trade_no` 格式和订单存在性，把 `TRADE_SUCCESS` 与 `TRADE_FINISHED` 作为支持的成功状态，其他状态返回 `fail`；
- 用 `BigDecimal.compareTo` 校验通知 `total_amount` 与订单应付金额；
- 状态只能从 `PENDING` 合法进入 `PAID`；已 `PAID` 的重复通知幂等成功，其他状态拒绝；
- 状态更新和冻结库存释放在同一事务内，并对并发重复回调加数据库级保护；
- 支付成功只执行 `frozen -= quantity`，不再次扣减可用库存；
- 增加独立支付完成时间，不能覆盖 `createTime`；
- 明确支付宝交易号的保存位置和唯一性；若沿用 `PaymentInfo`，需把其包结构、Repository 和关联关系整理清楚。

TDD 顺序：签名失败、订单号无效、金额不一致、非法状态、首次成功、串行重复、并发重复、库存释放中异常回滚。

PAY-002 独立跟踪支付表单所有权以外的前端确认缺口：同步返回页不能只凭浏览器查询参数显示成功或清理购物车，必须等待后端异步通知写入的订单状态；支付表单常见失败也应保持统一 `Response`。订单所有权仍由 SEC-001 统一处理，避免在 PAY-001 回调事务中混入认证边界重构。

### DB-001A 与 PAY-001 TDD 证据

迁移 Red 阶段先加入真实 MySQL 测试但不提供 SQL：全新临时数据库发现 0 个迁移而不是预期的 V1/V2，已有 schema 升级路径明确提示找不到 V1。加入 V1 当前完整 schema、V2 支付字段和 Flyway 配置后，全新数据库执行 2 个迁移，重复执行为 0 个；模拟已有 V1 schema 建立基线后只执行 V2，并保留原订单数据。迁移定向测试 2/2 通过。

支付 Red 阶段共运行 12 项测试，旧实现有 9 项失败：不支持的交易状态仍返回 `success`；金额不一致没有拒绝；非法订单状态仍变为 `PAID`；错误订单号泄漏为 `NumberFormatException`；支付时间和交易号没有保存；不同交易号被错误视为重复通知；同一支付宝交易号可支付两个订单；并发通知没有可验证的单次状态变更结果。签名失败、有效签名转发和库存异常事务回滚三项原有行为已经通过。

Green 阶段使用 `PENDING -> PAID` 条件更新决定唯一处理者，只有更新 1 行的事务才释放冻结库存；更新 0 行后使用锁定读取获取最新状态，解决 MySQL `REPEATABLE READ` 旧快照导致的重复通知误判。库存释放使用 `frozen >= quantity` 条件原子更新，支付状态、支付时间、交易号和全部库存释放处于同一事务。控制器 3/3、真实 MySQL 支付服务 9/9 通过；一次默认 Surefire 完整回归为 93/93，通过过程中没有调用真实支付宝或 OSS。

冷启动审查后的第二轮 Red 增加通知应用/收款方归属、`TRADE_FINISHED` 和默认关闭 Flyway 自动基线测试：10 项控制器与迁移测试中 4 项准确失败。Green 后回调验签继续核对 `app_id`/`seller_id`，支持支付宝定义的两个付款成功状态；Flyway 自动基线默认关闭，只允许受控旧库通过一次性变量显式开启。并发测试改为 6 个真实事务都先读到 `PENDING` 后再竞争，多商品回滚测试证明后续库存释放失败会撤销此前已完成的释放。合并前复核又补充了格式合法但数据库不存在的订单号测试，因此最终定向测试为迁移 4/4、控制器 6/6、支付服务 11/11。SEC-010 的本地网关与精确响应测试 3/3、真实沙箱只读探针 1/1 通过且控制台为空；当前默认完整回归在两个独立报告目录中均为 104/104。

真实支付宝沙箱交易不进入默认 Maven 测试。项目所有者按照[本机环境变量配置与启动指南](../guides/local-environment.md)核对八项支付宝变量并准备公网 HTTPS 回调后，可以在单独授权下完成一次人工闭环：沙箱买家付款、异步通知返回 `success`、订单变为 `PAID`、支付时间和交易号落库、冻结库存只释放一次。当前暂时没有可供支付宝服务器访问的 `notify_url`，因此合并前采用“RSA2 签名回调入口测试 + 真实 MySQL 支付事务测试 + 显式沙箱只读查询 + 可选支付表单检查”的分层验证，并明确记录真实异步通知未执行；`return_url` 由用户浏览器访问，只能检查同步跳转，不能代替异步通知。以后建立临时 HTTPS 隧道后再补做端到端闭环，不要求长期公网部署。

2026-08-10 当前沙箱分层验收已经完成可执行部分：本机 Java 17 安全检查证明应用私钥和支付宝公钥都是可解析的 2048 位 RSA 密钥，应用私钥能够完成 SHA256withRSA 自签名验证；显式 `AlipaySandboxConnectivityProbeIT` 使用随机不存在的订单号执行只读 `alipay.trade.query`，沙箱返回预期的 `ACQ.TRADE_NOT_EXIST`，证明当前 APPID、应用私钥签名和沙箱网关能够形成有效请求。首轮探针发现 SDK `sdk.biz.err` 输出业务参数，SEC-009 Red 阶段两个日志断言准确失败；关闭测试与应用运行时 logger 后目标日志测试 6/6，第二次真实探针仍通过且控制台无输出。当前分支的新 JAR 随后在隔离的 18080 端口启动，Flyway schema 版本 2、MySQL、Redis 和商品接口均正常；验收容器已删除且没有删除数据卷。由于没有公网回调，本次没有实际创建或支付沙箱订单，也没有宣称真实异步通知端到端通过。

## PAY-003：支付宝沙箱端到端人工验收

本项目定位为个人项目和面试展示，不进入真实资金生产环境，也不要求固定公网 IP、长期公网部署、正式商户签约或真实结算。为了让“支付宝沙箱接入”具有可复核的外部证据，在 SEC-001 完成支付表单订单所有权、PAY-002 完成服务端订单状态确认后，使用一次临时 HTTPS 公网入口完成端到端人工验收。

验收边界：

- `notify_url` 必须在验收期间能够被支付宝服务器访问；使用临时 HTTPS 域名即可，不要求购买公网 IP；
- `return_url` 由付款浏览器访问，只负责跳转，不能把查询参数当成支付成功；同机浏览器可以访问本机地址，为减少设备和平台差异也可以使用同一临时 HTTPS 域名；
- 如果付款浏览器和前端不在同一台电脑，`FRONTEND_URL` 也必须对该浏览器可达；这不改变异步通知才是可信支付结果的规则；
- 当前认证边界尚未完全收紧，SEC-001 完成前不得长期暴露整个后端端口；优先只开放通知和返回路径，验收结束立即关闭公网入口；
- 不把隧道凭据、沙箱账号、订单号、支付宝交易号、签名、请求正文或密钥写入仓库、截图和验收文档。

人工验收步骤：创建唯一待支付订单；生成网页支付表单；使用沙箱买家完成虚拟付款；确认支付宝侧交易状态、金额和商家归属；确认真实异步通知返回 `success`；确认本地订单为 `PAID`，`paidTime` 与支付宝交易号存在，可用库存不重复扣减且冻结库存只释放一次。重复通知幂等和中途异常回滚继续由自动化真实 MySQL 测试证明，不为人工演示记录原始通知内容。

完成后关闭临时公网入口，将本机回调配置恢复为明确的本地占位值。该任务只提供一次性沙箱闭环证据，不扩展退款、清结算、多支付渠道、消息队列或分布式事务，也不宣称生产资金能力。

## ORD-003：取消或超时关闭待支付订单

当前订单只支持 `PENDING -> PAID`。用户创建订单后如果不付款，可用库存已经减少而冻结库存会长期保留，因此需要独立的订单取消和超时关闭任务。本项不与 PAY-001 回调修复混在同一分支，避免同时改动已经完成审查的支付事务。

设计前必须明确：

- 手动取消只允许订单所有者操作，管理员是否可以关闭订单需要单独定义；权限规则与 SEC-001 的订单所有权规则保持一致；
- 只有 `PENDING` 可以进入取消或关闭状态；`PAID` 不能直接取消，退款属于未来独立支付任务；
- 取消或关闭时执行 `amount += quantity`、`frozen -= quantity`，订单状态和所有商品库存恢复必须处于同一数据库事务；
- 支付通知与取消同时到达时，数据库条件更新只能允许其中一个状态方向成功；失败的一方读取最新状态后按幂等或非法状态处理；
- 重复取消、重复超时处理不能重复恢复库存；
- 超时依据使用服务端创建时间和明确的超时时长，不能信任浏览器时间。第一版可使用受控的定时扫描或显式关闭入口，不引入消息队列。

TDD 顺序：订单所有权、正常取消恢复库存、非法状态、重复取消、多商品中途异常回滚、支付与取消并发、超时边界。库存恢复和并发状态竞争必须由真实 MySQL 测试证明。

## CACHE-001：Redis Cache-Aside

当前实际 key 为 `advertisement:product:{productId}`，TTL 随机 1800～3599 秒。改造必须保持广告位和商品详情前端行为兼容，并完成：

- 集中定义稳定 key；若迁移为通用商品 key，所有读写方同批切换或提供兼容读取；
- 商品详情缓存未命中时查库并回填；
- 保留随机 TTL，测试只断言范围；
- 以短 TTL 空值标记或等价方案防缓存穿透；
- 商品更新、删除提交成功后失效缓存；
- 广告更新更换商品时同时失效旧商品 key；
- `AdvertisementsServiceImpl` 和 `ProductServiceImpl` 使用 `RedisTemplate<String, Object>`，不再使用没有泛型参数的原始类型；
- 缓存读取先检查对象实际类型，再转换为 `ProductDTO`。遇到旧数据、错误类型或无法反序列化的数据时，应删除该缓存并从数据库恢复，不能直接强制转换导致商品接口失败；
- 当前项目通过 `RedisTemplate` 使用 Redis，没有定义 Spring Data Redis Repository。应在上下文测试证明 JPA Repository 仍能正常加载后，明确关闭 Redis Repository 自动扫描，避免每次启动进行无意义的 Repository 类型判断；
- `mvn compile` 不再出现由原始 RedisTemplate 引起的 unchecked 类型警告，应用启动不再出现未使用 Redis Repository 扫描产生的提示；
- 缓存故障不得破坏数据库主链路的正确性；
- 不声称没有测量依据的性能提升。

TDD 顺序：缓存命中、未命中回填、数据库不存在空值、错误缓存类型恢复、更新失效、删除失效、广告换品、Redis 异常降级、Spring 上下文中的 JPA/Redis Repository 边界。真实 Redis 测试还要验证序列化后的类型、TTL 范围和失效行为，不能只用 Mock 证明方法被调用。

## 测试真实性要求

- Service 单元测试验证业务结果和状态，不只验证 Repository 调用次数；
- 事务回滚、锁、条件更新和并发库存必须运行真实 MySQL 集成测试；
- Redis 序列化、TTL 和失效必须运行真实 Redis 集成测试；
- 支付回调业务与 SDK 验签边界分离，金额和状态测试不依赖真实支付宝；
- 每个缺陷先保存失败测试证据，再实现绿灯；没有看到正确失败的测试不算完成 Red 阶段。

## 推荐任务顺序

1. 先完成当前 DB-001A/PAY-001/SEC-009/SEC-010/TEST-002 的所有者审阅、分层沙箱验收、提交、PR、合并与归档。
2. 处理 SEC-001，先关闭匿名支付表单和跨用户购物车/订单访问风险。
3. 处理 PAY-002，使同步返回页只根据服务端订单状态展示结果，并保持支付表单失败响应兼容。
4. 执行 PAY-003 一次性沙箱端到端人工验收；它是验收任务，不扩展支付业务范围。
5. 处理 DB-001，补库存商品唯一约束，并在确认无引用和无数据后清理遗留 `PaymentInfo/payment_info`。
6. 处理 ORD-003，建立取消、超时关闭和冻结库存恢复规则。
7. 完成 CACHE-001 与 TEST-001 的 Redis Cache-Aside 实现和真实 Redis 测试。
8. 再处理 ORD-002 的结算请求幂等。

此顺序优先解决越权、数据库约束和冻结库存长期占用等正确性风险。若项目所有者更希望优先完成最初约定的 Redis 范围，可把第 5 项提前，但不能跳过当前分支的合并与归档流程。

- 当前分支的 DB-001A、PAY-001、SEC-009、SEC-010、TEST-002 只有在合并到项目所有者确认的集成分支并写入冷层证据后才从 BACKLOG 移除；CACHE-001 和 TEST-001 必须继续保持活跃，直到各自实现与测试完成；
