# Redis 缓存性能验证与热点保护计划

## 背景与当前边界

CACHE-001 已为商品详情建立通用 Cache-Aside：请求先读 Redis，未命中时读取 MySQL 并回填；商品不存在时短期缓存明确标记；商品和广告写入只在数据库事务提交后处理缓存；商品 TTL 随机 1800～3599 秒，不存在标记 TTL 随机 60～119 秒。广告创建和更新仍会提前缓存关联商品，原有热门广告商品预热行为得到保留。

真实 MySQL 8 和 Redis 6 集成测试已经证明功能、事务回滚和特定并发顺序正确。PERF-001 又在固定本机环境中建立了冷/热缓存、热点失效、无效 ID、Redis 停止与读写并发基线，但这些数据不能外推为生产容量，也不能笼统声称已经完全解决缓存穿透、缓存雪崩和缓存击穿。

## PERF-001：已完成的可重复性能基线

PERF-001 已通过 PR #11 合并。它在 DATA-001 稳定演示数据上固定代码、Java、MySQL/Redis、机器资源、数据规模、请求速率、持续时间和预热方法，使同一台机器可以重复比较，而不是只保留一次最好结果。最终数据与证据见[冷层交付记录](../archive/2026-08-12-cache-performance-baseline-delivery.md)。

### 对比状态

1. 缓存为空或显式关闭商品详情缓存时的数据库基线；
2. 当前 CACHE-001 在缓存已预热时的表现；
3. 若压测证明有必要，完成 CACHE-002 后再次执行相同场景。

不得通过清空用户 Redis 或删除用户数据库数据准备测试。测试只使用 DATA-001 的可识别演示数据或专用隔离数据，并只清理压测自己创建的 key。

### 必测场景

- 热缓存读取：重复访问已缓存的正常商品，观察 Redis 命中后是否明显减少 MySQL 查询；
- 冷缓存读取：商品第一次访问或缓存全部为空时，观察回填成本和数据库连接池压力；
- 热门商品过期：同一个热门商品 key 过期时并发请求到达，测量是否出现重复查库和请求等待；
- 相同无效 ID：反复请求同一个不存在商品，验证短期不存在标记能否减少重复查库；
- 随机无效 ID：每次请求不同的不存在 ID，确认当前短期标记无法直接阻止这一类攻击，并测量数据库压力；
- 大量 key 接近同时过期：验证随机 TTL 能否分散正常过期，同时记录仍会出现的峰值；
- Redis 不可用：验证请求回退 MySQL 时的错误率、延迟和数据库连接池压力，不把“功能能返回”误写成“性能仍正常”；
- 读写并发：读取商品详情的同时更新商品或切换广告，确认压测没有破坏 CACHE-001 已证明的一致性结果。

### 需要记录的指标

- 每秒完成请求数、平均延迟、P95 和 P99 延迟、错误率；
- Redis 命中、未命中、内存和连接使用情况；
- MySQL 查询次数、慢查询、锁等待、活动连接和连接池等待；
- 应用、MySQL 与 Redis 的 CPU 和内存；
- 热门 key 过期窗口内实际发生的商品数据库查询次数。

结果必须保存在新的冷层报告中，并提供命令、参数、数据规模和原始摘要。只有可重复结果才能进入简历/面试亮点，不预先规定或虚构目标 QPS。

## PERF-001 已确认实施基线

项目所有者于 2026-08-12 确认以下范围：

- 使用固定版本的开源 k6 Docker 镜像，不使用 Grafana Cloud；
- PERF-001 只测量当前实现，发现热点回填问题后仍由 CACHE-002 独立修改和复测；
- 使用独立 Compose 项目、独立 MySQL/Redis 数据卷和 DATA-001 的 300 本确定性商品，不连接或清理日常演示环境；
- backend 限制为 4 CPU/2 GiB、MySQL 为 2 CPU/2 GiB、Redis 为 1 CPU/512 MiB、k6 为 2 CPU/1 GiB；frontend 不进入性能环境；
- 增加默认启用的商品详情缓存配置开关，只在性能环境关闭以获得不含 Redis 失败开销的纯 MySQL 对照组；不得增加可被普通请求调用的缓存管理接口；
- 增加仅在性能配置启用、只在内部 Docker 网络访问的 Actuator 指标，采集 JVM、HTTP 和 Hikari 连接池；默认应用不得公开性能指标；
- 容量发现按每秒计划 1、10、25、50、100 个请求逐步执行，达到安全停止条件或饱和拐点时不继续增加；随后按实测结果选择低、中、高固定请求速率；
- 主要稳定场景预热约 20 秒、正式记录 60 秒并独立执行三次，最终使用中位数；事件型场景记录事件前、事件中和恢复后；
- Redis 故障只通过停止、健康确认、重新启动独立 Redis 容器模拟；不测试网络丢包、延迟注入或半连接；
- 读写并发通过真实 HTTP 管理员接口执行低频商品更新和高频详情读取；演示管理员密码只在运行时从被 Git 忽略的只读文件挂载到 k6，不进入 Compose 环境变量、命令行或结果文件，测试后恢复并核对数据库与 Redis；
- 提交 k6、环境、采集和报告生成脚本以及紧凑 JSON/CSV/图表；逐请求完整时间序列写入 Git 忽略目录；本轮不增加 Prometheus/Grafana。

QPS、P50/P90/P95/P99、最大延迟和系统饱和曲线属于本轮必须产出的真实结果；由于没有生产业务服务等级目标，第一轮不提前编造绝对 QPS 或延迟门槛。脚本从一开始必须对业务码、响应内容、恢复一致性和资源安全设置硬性失败条件；完成基线后再为 CACHE-002 和后续回归制定数据驱动的相对门槛。

## 本机资源保护

完整执行前先采样至少 30 秒；平均整机 CPU 必须低于 35%，可用物理内存不少于 8 GiB，C 盘可用空间不少于 15 GiB，E 盘不少于 5 GiB，Docker 和目标服务必须健康且 frontend 已停止。任何条件不满足时拒绝开始。

运行期间由独立看门狗采样资源。整机 CPU 连续 30 秒超过 85%、可用物理内存连续 10 秒低于 4 GiB、目标容器意外重启、Docker 失联、磁盘跌破安全线或连续大量错误时，只停止 k6 并保留环境供诊断，不删除数据卷或强制关闭 Docker Desktop。每个主要场景之间至少冷却 30 秒；两分钟内资源无法恢复则终止整套测试。

2026-08-12 开始前实测 frontend 的 Vite 轮询容器持续占约 54%～55% 的一个逻辑 CPU；停止后整机 CPU 从 35% 降至 16%，可用内存约 10.4 GiB，其他三个服务保持健康。该开发环境问题已并入 RUN-002，PERF-001 不修复它，只确保性能环境不启动 frontend。

同日首次执行正式 30 秒资源预检时，平均 CPU 为 17.33%、可用内存为 11.27 GiB、E 盘可用空间为 71.86 GiB，但 C 盘只剩 4.26 GiB，未达到 15 GiB 安全线，因此尚未构建或启动隔离性能环境。`docker system df` 的只读结果显示 Build Cache 共占 19.57 GB 且当前全部可回收；在项目所有者明确授权前，不自动删除构建缓存、镜像、容器、数据卷或用户文件。清理后必须重新执行完整预检，不能沿用本次结果。

项目所有者授权后已清理上述构建缓存，并使用 Docker Desktop 官方磁盘位置设置把 WSL 数据迁移到 `E:\DockerDesktopWSL`；迁移后的主数据 VHDX 约 29.04 GiB，现有镜像、容器和数据卷均保留，C/E 盘可用空间恢复到约 49.56/99.77 GiB。Docker 重启后的第二次 30 秒预检平均 CPU 为 24.8%，但可用内存仅 5.58 GiB，因此仍按规则拒绝构建和压测。只读进程快照显示 SpaceSniffer 约占 1.75 GiB、Docker WSL 约占 1.25 GiB；关闭非 Docker 用户应用需要项目所有者另行同意，不能把磁盘问题解决误写为整个资源预检已经通过。

## TDD 与执行顺序

1. 先写失败测试固定“缓存默认开启、性能配置关闭后不调用 Redis且业务响应不变”；
2. 先写失败测试固定 Actuator 默认不可访问、性能配置下仅暴露所需指标；
3. 先写可自动失败的脚本测试，证明资源不足、错误业务码和危险参数会拒绝执行；
4. 实现独立 Compose、固定资源、隔离数据准备、指标快照和恢复；
5. 先以每秒 1 个计划请求执行安全烟雾，确认正常商品、不存在商品、纯 MySQL、冷/热缓存和输出格式；
6. 验证 Redis 停止/恢复和真实 HTTP 读写并发的正确性，但不立即执行高负载；
7. 完成 Maven 回归、Compose 检查、脚本测试和独立冷启动审查；
8. 再执行受资源看门狗保护的正式容量发现和三次基线，生成报告并根据证据判断是否需要 CACHE-002。

## CACHE-002：按测量结果增加热点商品单次回填

当前缓存未命中的商品读取会使用 MySQL 商品行锁保证旧详情不会覆盖更新后的缓存，但它主要解决正确性问题。多个请求在同一热门商品过期后仍可能排队并依次查库，因此不能把当前实现描述成已经完整解决缓存击穿。

PERF-001 已提供实施依据：删除一个热门商品 key 后让 100 个虚拟用户同时各请求一次，虽然 100/100 响应正确，但产生 10 次 Redis 未命中、33 次 MySQL `SELECT`、9 次商品行锁等待和约 172 ms 累计锁等待，P95 约 39.79 ms；同机热缓存稳定场景 P95 约 3.56 ms。CACHE-002 因此进入实施阶段，但这些本机数据不是生产容量或生产服务等级承诺。

### 已确认范围与多实例边界

项目所有者于 2026-08-13 确认采用单个 Java 后端进程内、按商品 ID 协调的请求合并。Redis 正常且商品详情缓存未命中时，同一商品只允许一个请求成为数据库加载负责人；其他请求等待负责人完成后重新读取 Redis。不同商品使用不同协调记录，可以同时加载。该机制同时覆盖存在商品和不存在商品。

本轮不使用 Redis 分布式锁，也不承诺多个后端实例组成的集群全局只查询一次。如果以后同时运行三个后端实例，同一失效商品最多可能由三个实例各产生一名负责人；数据库正确性仍由共享 MySQL 商品行悲观锁保证。只有真实多实例压测证明“每实例一次回源”仍造成不可接受的数据库压力时，才评估带所有者校验、过期与故障处理的跨实例协调。

广告创建或更新后的商品提前缓存不参加 CACHE-002。广告管理是低频操作，现有独立新事务和商品行锁已经保证预热读取最新值；本轮不让后台管理事务与用户请求共享 500 ms 等待规则。

### 等待、失败与 CACHE-003 配合

- 等待者在 CACHE-002 中累计最多等待 500 ms；负责人完成后必须重新读取 Redis，不能直接使用负责人保存在 Java 内存中的商品对象。若重读时缓存又因商品更新而失效，只能使用原 500 ms 中的剩余时间参加下一轮，不得无限循环。
- 超过 500 ms 或等待线程被中断时返回 HTTP 503，继续使用统一 `Response`：业务码 `503`、消息“商品服务暂时繁忙，请稍后重试”。内部使用独立异常和指标与 CACHE-003 的数据库回退拒绝区分；线程中断时恢复 Java 中断标记。前端不自动重试，也不取消仍在执行的负责人。
- 负责人遇到数据库或事务异常时，本批等待者取得同一失败结果，不在本批中自动选择接替者重试；协调记录必须清除，之后的新请求可以重新尝试。数据库确认商品不存在属于正常结果：负责人写入 60～119 秒不存在标记，等待者重读后按现有“商品不存在”行为返回，不能统计为负责人失败或转成 503。
- Redis 基础设施故障不进入 CACHE-002，继续由 CACHE-003 的 5 秒临时绕过、最多 4 个数据库回退、50 ms 名额等待和 HTTP 503 保护处理。如果 Redis 在等待期间发生故障，等待者重读时转入 CACHE-003，不能绕过现有数据库容量保护。
- 协调记录在正常、异常、超时和中断路径都必须有确定生命周期，不能按商品 ID 永久积累。等待者超时只结束自身等待，不删除仍由负责人持有的协调记录。

### 事务边界

`ProductServiceImpl.getProductById` 不再为缓存读取和等待整体开启数据库事务。Redis 读取、CACHE-002 协调和最多 500 ms 等待位于事务外；只有负责人或 CACHE-003 获准回退数据库的请求调用独立 Spring 组件开启事务。该组件取得商品行悲观写锁，在事务内读取商品、规格和详情图并转换为完整 `ProductDTO`，在释放锁前回填 Redis，然后提交并释放锁。

数据库加载必须放在独立 Spring Bean 的公开事务方法中，不能依赖同一对象内部调用私有 `@Transactional` 方法。商品更新、删除和广告预热继续使用同一商品行锁；既有“旧详情不能在更新提交后重新长期写回缓存”和 MySQL 8 `REPEATABLE READ` 下不存在行与同 ID 创建协调测试必须继续通过。等待者不应取得商品行锁或占用数据库连接等待。

### 配置与指标

新增默认开启的 `tomatomall.cache.product-detail.single-flight.enabled` 和默认 `500ms` 的 `wait-timeout`，分别由 `PRODUCT_CACHE_SINGLE_FLIGHT_ENABLED` 与 `PRODUCT_CACHE_SINGLE_FLIGHT_WAIT_TIMEOUT` 覆盖。0、负数或无法识别的时间配置必须拒绝应用启动。关闭开关只用于同版本对照与紧急诊断，恢复当前每次未命中均可查库的行为。

沿用 Micrometer 记录负责人次数、等待者次数、等待成功、等待超时、等待中断、负责人失败、当前活动商品协调数、当前等待请求数和等待耗时。指标不使用商品 ID、用户名、Token 或其他会导致数据量无限增长或泄露信息的标签。Java 指标与 MySQL 查询/锁状态必须交叉验证，不能只用 Mock 调用次数声称完成。

### TDD 与验收顺序

1. 配置测试先证明默认启用、500 ms 可覆盖，以及 0、负数和非法时间拒绝启动；
2. 失败并发测试证明同一存在商品只有一名负责人、等待者重读 Redis，不存在商品也只确认数据库一次；
3. 证明不同商品互不阻塞，负责人异常会释放全部等待者并清理记录，后续请求可以重新加载；
4. 证明累计 500 ms 超时、线程中断、等待者不取消负责人，以及所有活动/等待计数最终归零；
5. 证明 Redis 在等待期间故障时转入 CACHE-003，而不是绕过其 4 个名额和 50 ms 保护；
6. 拆出独立事务加载组件，证明缓存命中和等待者不进入数据库加载事务，负责人仍在商品锁内完整读取并回填；
7. 真实 MySQL 8/Redis 6 测试覆盖存在/不存在商品、不同商品并行、异常清理、等待超时、更新并发、不存在行与同 ID 创建，以及 CACHE-003 兼容；
8. 复跑 CACHE-001 的商品更新/删除、短期不存在标记、广告预热和事务回滚测试，再执行 Maven 编译、完整测试与 `git diff --check`；
9. 资源安全线允许时，在相同代码和容器资源下关闭开关运行三轮、开启开关运行三轮，每轮删除同一热门商品 key 后由 100 个虚拟用户各请求一次；
10. 每轮必须完成 100 个正确响应，HTTP/业务错误、503 和丢弃均为 0；负责人恰好 1、等待超时与负责人失败为 0、测试后活动协调与等待数为 0；MySQL `SELECT` 增量不超过 18、商品行锁等待为 0、Hikari 连接池等待和超时为 0；开启后的 P95 三轮中位数必须低于关闭时，P99 不得明显倒退。

高负载执行继续遵守 PERF-001 安全线：开始前 30 秒平均 CPU 低于 35%、可用物理内存不少于 8 GiB、C/E 盘空间达标且目标服务健康。资源不足时不关闭用户其他程序、不降低安全线、不把小规模测试冒充 100 请求验收。

### 非目标

CACHE-002 不引入 Redis 分布式锁、微服务、消息队列、Kubernetes、热门名单、按商品配置等待时间、失败负责人自动接替、前端自动重试、动态等待时间或 Prometheus/Grafana。它不处理持续随机无效 ID 的完整穿透治理，不修改广告预热、订单、库存、支付或废弃 AI 功能。

### 2026-08-14 当前实现与验证状态

当前开发分支已经完成单个 Java 后端进程内按商品 ID 合并请求、500 毫秒累计等待、独立事务数据库加载、统一 HTTP 503、无商品 ID 标签的 Micrometer 指标，以及与 CACHE-003 故障保护的衔接。独立审查发现并推动修复了“截止时间检查与登记负责人之间仍可能过期”的并发竞态、合法截止值恰好为 0 时会重置等待时间、正式脚本可用少于 100 个虚拟用户运行、脚本信任本地开关文件、旧镜像可能被复用、100 次共享迭代不等于每个虚拟用户各一次，以及只检查压测结束时连接池排队数等问题。

## CACHE-003：Redis 故障时的有界等待与数据库保护

### 已确认的业务行为与参数

项目所有者于 2026-08-13 确认：Redis 是商品详情的加速层，MySQL 仍是最终可信来源。连接失败、连接关闭或命令超时等基础设施故障第一次发生时，应用立即临时绕过 Redis 5 秒；单个缓存值反序列化失败或类型错误只处理当前 key，不得停用全部缓存。

- Redis 建立连接最多等待 250 ms，命令最多等待 500 ms，均通过环境变量配置；
- 故障绕过期间，商品详情最多允许 4 个请求同时回退 MySQL；等待名额最多 50 ms；
- 超出回退容量时返回 HTTP 503，正文继续使用 `code/msg/data`，消息为“商品服务暂时繁忙，请稍后重试”；
- 前端商品详情页显示后端明确消息，不自动重试，不全面重构 Axios；
- 5 秒后只允许一个请求检查恢复，其他请求继续走受限数据库回退；
- Redis 恢复后先用 `SCAN` 分批清理 `product:detail:v1:*`，禁止 `FLUSHDB`，清理成功后才恢复缓存读取；清理失败则继续绕过；
- 读取、商品/不存在标记回填、创建/更新/删除后的失效以及广告预热都使用同一故障保护；缓存写入、删除或预热失败不得回滚已经成功的数据库事务；
- 单体本机/面试范围内不引入 Redis Cluster、Sentinel、多实例状态共享、消息队列、Prometheus、Grafana 或 Toxiproxy。

恢复前清理商品缓存用于处理一个重要边界：Redis 故障期间商品可能已经在 MySQL 更新，但提交后的缓存删除失败；Redis 重启后可能恢复出旧值。CACHE-003 不承诺数据库与 Redis 强一致，但不得在确认恢复时主动重新启用这些可能过期的商品缓存。

### 运行指标

使用已有 Spring Boot Actuator 与 Micrometer 记录 Redis 故障次数、临时绕过次数、数据库回退成功/拒绝、恢复检查、恢复成功和清理失败；同时记录故障状态 `0=正常、1=临时绕过、2=恢复检查` 以及当前活动数据库回退数。默认应用不新增公开指标端口，性能环境继续只在内部 Docker 网络读取。

### TDD 顺序

1. 配置测试先证明 250 ms、500 ms、5 秒、4 个名额和 50 ms 可由环境变量覆盖；
2. 连接/命令超时第一次失败立即绕过，单 key 损坏不打开全局绕过；
3. 绕过期间不再访问 Redis，正常未命中仍保持既有数据库读取与回填行为；
4. 并发测试证明只有 4 个故障回退进入 MySQL，第 5 个请求在 50 ms 后拒绝，正常和异常路径都释放名额；
5. MockMvc 证明拒绝结果为 HTTP 503 和统一 `Response`；
6. 并发恢复测试证明同一时刻只有一个检查者，只清理商品 key，清理失败不提前恢复；
7. 真实 MySQL/Redis 测试证明故障期间更新商品、恢复后不会重新读取旧缓存；
8. 指标测试证明故障、绕过、回退、拒绝和恢复计数与业务结果对应；
9. 前端构建和实际页面验证明确 503 提示且没有自动重试；
10. 使用现有隔离 PERF Compose 停止/恢复真实 Redis，并以可控测试替身覆盖“连接仍在但命令卡住”的时间边界。

### 故障与恢复验收

真实故障场景仍采用 50 QPS、10 秒。所有已发请求必须在 2 秒内结束，P99 不超过 1 秒；不允许网络超时、k6 丢弃、HTTP 500、错误商品或无法解析响应。业务结果只能是正确的 HTTP 200，或容量保护产生的 HTTP 503；MySQL 连接池超时必须为 0，后端/MySQL 不得意外重启。

Redis 重启后最多 10 秒完成单检查者恢复和商品缓存清理；恢复阶段商品请求全部正确、不再产生保护性 503，并确认未清理非商品 key。这些阈值只适用于固定本机环境，不是生产服务等级承诺。

2026-08-13 的 CACHE-003 实测使用隔离 PERF Compose、300 本演示商品、50 QPS 和 10 秒 Redis 完全停止。停机阶段发出 501 个商品详情请求，全部完成且业务失败率为 0、丢弃为 0，P99 为 506.81 ms、最大 508.51 ms；本机数据库容量足以承接该强度，因此这次没有出现保护性 503。Redis 重启后 2.879 秒完成共享连接重置、单检查者恢复和商品 key 清理；随后 501 个请求全部正确，P99 为 13.71 ms。测试还证明故障期间修改的商品评分在恢复后读到数据库新值，预置的非商品 key 未被删除，HikariCP 数据库连接池超时为 0，后端和 MySQL 重启次数均为 0。这只是固定本机与固定数据规模的验收结果，不能外推为生产容量。

独立审查随后把恢复轮询收紧为“每一次请求都必须返回 HTTP 200、业务码 `200` 和正确商品 ID”，不再接受或吞掉 HTTP 503、500、网络超时或错误商品。该脚本修复完成后，本机可用内存约 5.26 GiB，低于 PERF-001 规定的 8 GiB 代表性测试安全线；按照项目所有者“不得关闭其他程序腾出内存、不得降低安全线”的要求，没有强行重跑 50 QPS。生产代码已重新完成 38 类 219/219 Maven 回归，脚本静态检查 6/6；上述 v4 数据仍证明生产实现的故障和恢复行为，但不能声称收紧后的脚本已经再次完成真实高负载运行。

## 穿透、雪崩和 Redis 故障的后续判断

- 相同不存在 ID：CACHE-001 已有 60～119 秒不存在标记，真实 Redis 测试已覆盖；
- 大量随机不存在 ID：短期标记无法复用，应先做 ID 格式/范围校验、接口限流和压测，再依据数据量与误判容忍度决定是否需要布隆过滤器；
- 正常 key 集中过期：CACHE-001 已用随机 TTL 降低同一秒过期概率，但 Redis 重启、数据丢失或全量冷启动不会被随机 TTL 解决；
- Redis 整体不可用：当前会回退 MySQL，后续应根据压测决定是否需要限流、快速失败、分批预热或熔断保护，不能把数据库回退当成无限容量；
- 多实例和高可用：本项目当前定位是本机/面试演示，暂不引入 Redis Cluster、消息队列或完整生产容灾架构。

## 任务顺序与完成标准

1. DATA-001 在独立演示数据库准备可重复、不会清空数据库的 300 本商品与规模用户；
