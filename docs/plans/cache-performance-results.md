# PERF-001 Redis 与 MySQL 本机性能测量结果

本文记录 `codex/perf-cache-baseline` 尚未合并阶段的可复核结果。它属于温层活跃报告，不是已交付能力声明；合并到个人 `master` 后才转入冷层，并同步判断是否更新简历/面试亮点。

## 测量环境与方法

- 代码基线：`master@62acf0f8`，开发分支 `codex/perf-cache-baseline`。
- 工具：开源 `grafana/k6:2.0.0`，不使用 Grafana Cloud；Java 为 Temurin 17.0.19，MySQL 为 8.0.46，Redis 为 6.2.23。
- 镜像固定：性能 Compose 在标签之外固定本次实际使用的摘要：MySQL `sha256:7dcddc...ae2b`、Redis `sha256:ec5e18...8c23`、k6 `sha256:a33a0c...23c`、指标采集镜像 `sha256:94e9e4...44e6`。省略号只是文档显示缩写，Compose 保留完整摘要。
- 隔离环境：独立 Compose 项目 `404notpure-perf`、独立 MySQL/Redis 数据卷、数据库 `tomatomall_demo`；不连接或清理日常数据。
- 数据：DATA-001 seed `404` 生成 300 件商品、300 条库存、1200 条规格、300 张本地详情图、6 条广告及演示账户。
- 资源上限：后端 4 CPU/2 GiB，MySQL 2 CPU/2 GiB，Redis 1 CPU/512 MiB，k6 2 CPU/1 GiB；不启动前端。
- 容量探测：1、10、25、50、100 QPS 依次运行 15 秒，全部没有业务错误或丢弃请求，因此正式档位选择 10、50、100 QPS。这里的“高档”只表示本机本轮测试范围，不代表系统极限。
- 正式稳定场景：20 秒预热，60 秒记录，独立执行三次并取中位数；轮间冷却 30 秒。
- 正确性硬条件：业务响应内容、HTTP 传输、检查断言必须全部正确，计划请求不得被 k6 丢弃。Redis 故障场景未满足这些条件，因此明确记录为失败，不从报告中删除。
- 资源保护：正式测试前 30 秒平均 CPU 20.47%、可用内存 8.99 GiB；最终有效结果期间 CPU 峰值 62%、最低可用内存 6.95 GiB，C/E 盘最低约 43.92/98.55 GiB。未触发连续 CPU、内存或磁盘停止条件，三个核心容器无重启和内存不足退出。本轮没有关闭其他用户应用来腾出内存。

运行时完整 JSON、日志与快照位于 Git 忽略的 `performance/results/`；可提交脚本会生成 `summary.csv`、`medians.csv`、Markdown 摘要和 SVG 图表。正式 `formal-v2` 结果不保存演示管理员密码、JWT（登录令牌）或 k6 `setup_data` 运行时认证数据；早期探索性结果曾包含仅由商品 ID 组成的 `setup_data`，它们不作为正式证据，也没有包含密码或令牌。

下表三轮数据是在硬阈值最终收紧前生成的：当时脚本允许检查成功率高于 99%、业务与传输错误率低于 1%。原始数据本身实际均为检查成功率 100%、业务错误 0、传输错误 0、丢弃 0，因此表格数值仍有效；但不能把旧结果说成由当前严格阈值直接把关。当前脚本已经改为必须 100% 正确且丢弃数为 0，并通过后文所列代表性复测验证。正式套件也会拒绝旧前缀、缺少任意一轮、缺少整组场景或某轮硬阈值失败，避免混入旧结果或生成不完整中位数。

## 稳定场景三轮中位数

| 场景 | 完成 QPS | P50 | P95 | P99 | 业务错误 | Redis 命中增量 | MySQL `SELECT` 增量 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 关闭商品详情缓存，10 QPS | 10.008 | 5.165 ms | 9.407 ms | 26.484 ms | 0 | 0 | 1812 |
| 热缓存，10 QPS | 10.007 | 3.658 ms | 6.408 ms | 15.693 ms | 0 | 601 | 9 |
| 关闭商品详情缓存，50 QPS | 49.975 | 3.312 ms | 5.829 ms | 12.914 ms | 0 | 0 | 9012 |
| 热缓存，50 QPS | 49.970 | 2.332 ms | 4.111 ms | 11.931 ms | 0 | 3000 | 12 |
| 关闭商品详情缓存，100 QPS | 99.937 | 3.041 ms | 5.066 ms | 10.384 ms | 0 | 0 | 18012 |
| 热缓存，100 QPS | 99.942 | 2.143 ms | 3.561 ms | 7.371 ms | 0 | 6000 | 12 |
| 固定不存在 ID，100 QPS | 99.931 | 2.741 ms | 4.570 ms | 10.426 ms | 0 | 6000 | 10 |
| 每次变化的不存在 ID，100 QPS | 99.920 | 3.788 ms | 6.551 ms | 17.019 ms | 0 | 0 | 6010 |
| 100 QPS 读取加 1 QPS 管理员更新 | 100.803 | 2.263 ms | 4.748 ms | 28.370 ms | 0 | 5940 | 317 |

在 100 QPS 档，热缓存相对关闭缓存的三轮中位数约降低 P50 29.5%、P95 29.7%、P99 29.0%，并将 MySQL `SELECT` 中位数从 18012 降到 12，约减少 99.93%。这些百分比只适用于本机、当前数据与固定资源，不可外推为生产环境收益或容量。

同一不存在 ID 的短期标记有效：约 6000 个请求只增加 10 次 MySQL `SELECT`。每次变化的无效 ID 无法复用标记：约 6000 个请求增加 6010 次 `SELECT`，约为固定 ID 的 601 倍。当前实现能缓解重复查询同一个不存在商品，但不能据此声称已经解决持续随机无效 ID 的缓存穿透；后续应先评估 ID 范围校验和限流，再决定是否需要布隆过滤器等额外结构。

读写场景通过真实管理员 HTTP 接口执行，并在每轮结束恢复商品原描述后重新读取验证。三轮业务错误均为 0；MySQL 行锁等待分别增加 1、2、1 次，Hikari 数据库连接池没有等待或超时。该结果支持当前并发正确性，但不代表多实例或生产写入流量。

## 冷启动、热门商品与 CACHE-002

- 清空全部 300 件商品详情缓存后，以 100 QPS 运行 60 秒：完成 6001 个请求，业务错误与丢弃均为 0，P95 约 4.807 ms、P99 约 9.175 ms；出现 158 次 Redis 未命中和 483 次 MySQL `SELECT`。这是一轮“全部缓存先清空后的冷缓存流量测试”，但脚本没有记录不同商品 ID 的覆盖数，因此不能声称 300 件商品都至少被请求一次；它也不是对随机 TTL 自然过期分布的长时间统计。
- 删除一个热门商品 key 后让 100 个虚拟用户同时发出各一次请求：100/100 正确，P50 约 29.012 ms、P95 约 39.794 ms、P99 约 42.993 ms；出现 10 次 Redis 未命中、33 次 MySQL `SELECT`、9 次行锁等待，累计锁等待约 172 ms。

热门商品场景说明数据库行锁维持了正确性，但多个请求仍会排队并重复读取数据库；与热缓存 100 QPS 的 P95 约 3.561 ms 相比，瞬时失效窗口延迟明显上升。因此 CACHE-002 已有实施依据，应增加有界、异常可释放的“同一商品单次回填”协调，并使用相同场景复测。不能把本次结果写成当前已经完全解决缓存击穿。

## Redis 完全停止与 CACHE-003

第一次故障脚本曾被 `docker compose run` 自动启动依赖服务，造成 Redis 实际已恢复却误以为仍处于故障。脚本增加 `--no-deps` 并用快照确认 `redis.available=false` 后重新执行，旧结果不作为证据。

最终故障场景为计划 50 QPS、10 秒：Redis 停止期间只开始 3 个 HTTP 请求，没有任何业务请求完整返回，401 个计划请求未能发出，硬阈值失败。代码虽然捕获 Redis 读异常并计划回退 MySQL，但默认客户端连接等待使请求长时间阻塞，因此当前不能声称 Redis 完全停止时能够及时回退数据库。

脚本随后自动重启 Redis；恢复阶段同样以 50 QPS 运行 10 秒，完成 501 个业务请求，业务错误 0、丢弃 0、检查成功率 100%，Redis 最终返回 `PONG`，后端仍能读取 300 件商品。说明恢复路径正常，但故障窗口可用性不达标。

CACHE-003 应独立处理 Redis 连接与命令超时、请求堆积、数据库回退容量和限流/快速失败策略。本轮 PERF-001 只测量并登记缺陷，不在同一批次顺手修改超时参数。

## 可以与不可以得出的结论

可以得出：在本机固定资源和最高 100 QPS 稳定负载下，热缓存能可重复地减少 MySQL 读取并降低详情请求尾延迟；固定不存在 ID 标记有效；真实 HTTP 低频更新与高频读取保持正确；热点失效存在重复回源和锁等待；Redis 完全停止时当前请求会被连接等待阻塞，但重启后能恢复。

不能得出：系统生产极限是 100 QPS；已经完整解决缓存穿透、雪崩或击穿；Redis 故障能够无感回退；多实例、跨机器、Redis Cluster、网络丢包或真实生产流量已通过；百分比收益可直接用于云环境或简历中的生产数据。

## 后续验证

1. TDD 的失败阶段（Red，即先用失败测试证明缺口）包括：缓存开关测试最初因 `ProductDetailCache` 没有开关构造参数而编译失败；性能 YAML 测试最初发现未加引号的 `OFF` 会被解析为布尔值；资源脚本测试最初发现磁盘安全参数缺失。实现后（Green，即修复后通过）分别形成缓存开关单元测试、配置解析测试和资源保护脚本测试。结果汇总器还用脚本测试证明缺少第三轮时会失败、补齐三轮后才生成中位数。
2. 审查修复后的最终 Maven 回归为 32 个测试类、201/201，失败、错误和跳过均为 0；Compose 配置解析通过，PowerShell 资源保护为 9/9，结果完整性脚本为 4/4，看门狗异常清理集成测试为 1/1，`git diff --check` 通过。结果脚本覆盖缺少第三轮、正式前缀复用和失败后只残留 before 快照时拒绝重用结果名；清理测试证明模拟监控异常后只停止 k6，后端、MySQL、Redis 保持运行且没有重启。第一次最终回归曾因误留的两个 Maven 容器并行修改同一数据库，产生一次商品总数 312/311 的交叉干扰；停止由本任务误启动的旧测试容器后，失败类单独重跑 11/11，通过，随后唯一一轮完整回归通过。该受污染轮次不作为交付证据。
3. 当前严格脚本完成两次 1 QPS、5 秒安全烟雾，均为 6/6 请求正确；第二次还验证了新增的异常清理块没有破坏正常路径。计划进行更高负载的代表性复测时，新的 30 秒预检测得平均 CPU 13.4%、C/E 盘可用约 44.01/98.42 GiB，但可用内存只有 7.74 GiB，低于 8 GiB 开始线，因此脚本按设计拒绝执行。项目所有者明确禁止关闭其他内容腾出内存，本轮不会降低安全线强行运行；这些烟雾不能替代高负载复测。
4. CACHE-003 优先修复 Redis 完全停止时的有界超时与保护，并以相同 50 QPS 故障/恢复场景复测。
5. CACHE-002 实现同一热门商品的受控单次回填，以相同 100 请求瞬时场景复测回源、锁等待和延迟。
6. 持续随机无效 ID 先评估接口 ID 范围校验与限流，不在没有误判和数据规模依据时直接引入复杂过滤结构。
