# 404NotPure 简历与面试亮点总结

## 文档用途

本文档是 404NotPure 项目的长期维护材料，用于回答三个问题：

1. 目前有哪些能力已经具备足够证据，可以写进简历；
2. 面试官继续追问时，应该如何说明业务问题、技术方案、设计取舍和测试证据；
3. 哪些内容仍然只是计划或部分完成，暂时不能包装成已有能力。

本文档不是宣传稿。所有结论必须能追溯到已经合并到个人 `master` 的代码、测试、Pull Request 或冷层交付记录。不能用“高并发”“生产级”“性能提升百分之多少”等宽泛词语替代具体实现，也不能把 BACKLOG 中的计划项提前写成现有能力。

根目录未跟踪的 `面试回答指南.md` 是项目所有者的私人文件，不属于本文档的来源，也不会由自动化流程读取、修改或提交，除非项目所有者以后单独明确授权。

## 项目定位与一句话介绍

404NotPure（TomatoMall）是一个由多人课程项目继续演进而来的个人在线图书商城，采用 Java 17、Spring Boot 2.7.6、Spring Data JPA、MySQL 8、Redis 6、Vue 3 和 TypeScript。当前个人改进重点不是增加展示性页面，而是把下单、库存、支付、对象存储、数据库迁移和测试流程改造成具有明确正确性证据的后端链路。

本文档会使用一些常见技术缩写，含义如下：

- **JPA**：Java 的数据库持久化接口规范，本项目使用 Hibernate 实现；
- **OSS**：阿里云对象存储服务，用于保存头像、商品图和广告图；
- **RAM 用户**：阿里云中供应用访问云资源的独立身份，可以单独配置权限；
- **RSA2**：支付宝使用的 RSA 签名方案，摘要算法为 SHA-256，用于验证通知来源和内容完整性；
- **SDK**：第三方服务提供的软件开发工具包，本项目使用支付宝和阿里云 OSS 的 Java SDK；
- **MIME 类型**：HTTP 中声明的文件内容类型，例如 `image/png`；
- **UUID**：随机性很高的唯一标识符，本项目用它生成不依赖用户文件名的 OSS 对象名称；
- **Flyway**：按照版本顺序执行数据库结构变更脚本的迁移工具；
- **TDD**：测试驱动开发，先写能够复现缺陷的失败测试，再实现修复并保持测试通过；
- **数据库事务**：一组数据库操作要么全部提交，要么在异常时全部撤销，避免只完成其中一部分；
- **条件原子更新**：把“条件是否满足”和“数据修改”放在同一条数据库更新语句中执行，其他并发请求不能插入到这两个动作之间；
- **幂等**：同一业务通知或请求重复执行多次，最终业务结果仍只产生一次；
- **冻结库存**：已经被待支付订单占用、不能再出售，但尚未最终确认售出的库存；
- **Cache-Aside**：应用先读缓存，未命中再查数据库并回填，数据库更新后主动让缓存失效的常见缓存模式；
- **Surefire**：Maven 执行 JUnit 测试的组件；
- **QPS**：每秒处理的请求数量，是吞吐量指标，必须经过压力测试后才能报告。
- **Pull Request（PR）**：把开发分支合并到主分支前，用于集中展示差异、审查和记录结论的 GitHub 流程；
- **持续集成（CI）**：代码推送后由远端系统自动执行编译、测试和检查的流程；当前项目尚未配置远端 CI。

适合在简历项目介绍中使用的一句话：

> 基于 Spring Boot、JPA、MySQL、Redis 与 Vue 3 实现在线图书商城，并围绕订单库存一致性、支付宝异步通知幂等、数据库版本化迁移和 OSS 图片安全完成后端可靠性改造。

这句话没有声称完整生产部署、真实资金支付、完整订单生命周期或已经完成的 Redis Cache-Aside，因为这些能力目前仍在 BACKLOG 中。

## 亮点一：订单与库存一致性

### 解决的实际问题

旧下单流程采用“先读取库存，再在 Java 对象中修改并保存”的方式。多个事务可能同时读到同一份可用库存，随后各自认为库存充足，因此仅增加一个普通事务注解并不能自动防止并发超卖。

### 当前实现

- `OrderServiceImpl.addOrder` 使用 `@Transactional` 包含请求校验、用户和商品读取、库存冻结、订单保存与订单项保存。
- 同一请求中的重复商品先按照商品 ID 汇总，避免把总购买量拆成多行绕过校验；使用 `Math.addExact` 拒绝整数溢出。
- `StockPileRepository.freezeStockIfAvailable` 通过一条 MySQL 条件更新执行 `amount -= quantity`、`frozen += quantity`，只有 `amount >= quantity` 时才成功。
- SQL 同时拒绝一个商品对应多条库存记录的异常数据，避免随意选择其中一条继续下单。
- 任意商品库存不足、库存数据异常或订单保存失败都会抛出异常，由同一事务回滚之前已经完成的库存冻结和订单写入。
- 服务端使用数据库商品价格和购买数量计算 `BigDecimal` 订单总额，不信任客户端价格。

### 为什么选择条件原子更新

项目是单体应用，库存最终事实位于 MySQL，业务规则也是简单的“库存足够才扣减”。因此把判断条件和修改放入同一条 SQL，可以直接利用数据库对单行更新的原子性，减少显式锁管理和跨系统协调。

这并不意味着悲观锁或乐观锁“不好”：悲观锁适合读取后需要复杂计算和多次修改的场景；乐观锁适合冲突较少且允许重试的场景。当前链路只需要按数量改变两个库存字段，条件原子更新更直接，也更容易通过更新行数判断成功或失败。

### 测试证据

- 正常订单创建后状态为 `PENDING`，可用库存减少，冻结库存增加。
- 重复商品被汇总为一个订单项，并按总数量计算金额和库存。
- 后续商品库存不足会回滚前一个商品已经完成的库存冻结。
- 订单持久化失败会回滚库存。
- 库存记录缺失或同商品多条库存记录时不会创建订单。
- 16 个线程争抢 1 件库存的真实 MySQL 测试中，成功订单和冻结库存总量不会超过 1；重复库存修正版测试又连续运行 3 次通过。
- ORD-001 定向测试 27/27，合并前完整回归 79/79。

### 面试常见追问

**问：加上 `@Transactional` 为什么还不够？**

答：事务保证一组操作一起提交或回滚，但普通隔离级别下，两个事务仍可能先后读到相同库存。必须让“库存是否足够”和“扣减库存”成为不可分割的数据库动作，或者使用合适的锁/版本控制。项目选择带 `amount >= quantity` 条件的原子更新，并通过受影响行数判断是否成功。

**问：为什么库存有 `amount` 和 `frozen` 两个字段？**

答：创建待支付订单时先把库存从可用量移动到冻结量，避免其他订单继续购买；支付成功后只减少冻结量，不再次扣减可用量。未来取消或超时关闭订单时，应该把冻结量恢复到可用量，但 ORD-003 还未实现这一段。

**问：能否直接说项目支持高并发？**

答：不能。当前证据只证明指定的数据库并发争抢场景不会超卖，没有做 QPS、延迟、连接池容量或长时间压力测试。简历应写“并发下单时库存不会被扣成负数”及对应测试，不写没有测量依据的吞吐量。

## 亮点二：支付宝异步通知可信处理与并发幂等

### 解决的实际问题

支付平台的异步通知可能重复发送，也可能并发到达。仅验证签名仍不够：有效签名只能证明参数来自支付宝，不能证明通知属于当前应用、当前收款方、当前订单和正确金额；如果先读订单状态再直接修改，两个并发通知也可能重复释放冻结库存。

### 当前实现

- Controller 使用支付宝 SDK 完成 RSA2 验签。
- 验签通过后继续核对 `app_id`、`seller_id`、`out_trade_no`、`trade_no`、`total_amount` 和 `trade_status`。
- 只接受 `TRADE_SUCCESS` 和 `TRADE_FINISHED` 两种项目支持的成功状态。
- 订单金额从数据库读取，使用 `BigDecimal.compareTo` 做数值比较，避免 `19.9` 与 `19.90` 这类字符串格式差异。
- 只有 `PENDING` 订单可以通过条件更新变为 `PAID`；数据库中同时保存独立的 `paidTime` 和支付宝交易号。
- 支付宝交易号建立唯一约束，防止同一交易号被用于两个订单。
- 并发竞争中没有更新到订单的事务，会使用数据库写锁重新查询最新订单状态；只有“订单已经支付且交易号相同”才把当前通知作为合法重复通知处理，不同交易号会被拒绝。
- 订单状态、支付结果和所有订单项的冻结库存释放处于同一事务；任何一项释放失败都会回滚整个支付结果。

### 测试证据

- 签名失败、错误应用、错误收款方和不支持的交易状态不会进入支付服务。
- 金额不一致、订单号格式错误、订单不存在和非法来源状态都不会改变订单或库存。
- 同一交易号的串行重复通知不会重复释放库存。
- 不同交易号不能重复支付同一订单，同一交易号也不能支付两个订单。
- 多个彼此独立的真实数据库事务并发处理同一订单通知时，只有一个事务完成状态更新和库存释放。
- 单商品或后续商品释放失败会回滚支付状态、支付时间、交易号和此前完成的库存释放。
- 回调 Controller 6/6、真实 MySQL 支付事务 11/11、Flyway 迁移 4/4。

### 面试常见追问

**问：为什么签名通过后还要校验应用、收款方和金额？**

答：验签只证明参数未被篡改且由支付宝签发。系统仍需要确认这份通知属于自己的应用和商户，订单号在本系统存在，金额等于服务端订单金额，交易状态是本项目认可的成功状态。否则可能把另一业务或错误金额的合法通知应用到当前订单。

**问：重复通知为什么不能只写 `if (status == PAID) return`？**

答：如果不比较交易号，另一个不同交易也可能被误认为合法重复通知；如果并发事务同时读到 `PENDING`，普通先读后写仍可能重复处理。项目使用来源状态条件更新决定唯一处理者；没有更新成功的竞争事务再加数据库写锁查询最新订单，确认已支付订单的交易号与当前通知一致。

**问：支付成功为什么是释放冻结库存，而不是再次扣减可用库存？**

答：可用库存已经在创建 `PENDING` 订单时扣减并转入冻结库存。支付成功只确认这部分库存已售出，因此减少冻结量；再次减少可用量会重复扣库存。

### 必须诚实说明的边界

- 已完成支付宝 SDK 接入、只读沙箱连通探针和回调业务测试，但尚未使用沙箱买家完成一次真实网页付款，也没有收到支付宝服务器通过公网 `notify_url` 发来的真实异步通知。

- 同步 `return_url` 页面仍需改为查询服务端订单状态，由 PAY-002 跟踪。
- 因此可以写“完成异步通知处理和幂等设计”，不能写“已完成支付宝生产支付闭环”或“真实资金交易已上线”。

## 亮点三：Flyway 数据库版本化迁移

### 解决的实际问题

旧项目使用 Hibernate `ddl-auto: update` 自动修改数据库。这种方式方便开发，但数据库变化缺少明确版本、执行顺序、审查记录和失败恢复依据。新增支付时间和支付宝交易号时，如果继续依赖自动改表，就很难证明全新数据库与已有数据库都能安全升级。

### 当前实现

- V1 保存当前完整商城结构基线，V2 增加订单支付时间、支付宝交易号和唯一索引。
- Hibernate 改为 `ddl-auto: validate`：Flyway 负责改变结构，Hibernate 只检查实体映射是否匹配。
- `baseline-on-migrate` 默认关闭，陌生的非空数据库不会被自动当成 V1。
- 只有经过备份和人工核对、确认与 V1 一致的旧数据库，才允许临时显式开启一次基线操作，随后必须恢复关闭。
- 已经执行过的 V1/V2 不再修改；后续结构变化必须新增 V3、V4 等迁移。

### 测试证据

- 默认配置明确关闭自动基线。
- 陌生非空 schema 未显式授权时迁移失败，不会继续修改表。
- 全新数据库执行 V1+V2 后通过全部 JPA 实体结构验证，重复执行不会重复改变结构。
- 由 Hibernate 生成的旧结构移除支付字段后，显式基线并执行 V2，可以保留已有订单并再次通过全实体验证。

### 适合面试的总结

> Flyway 的价值不是“多用了一个库”，而是把数据库结构从运行时隐式副作用变成可审查、可排序、可重复验证的版本化变更。项目还特别关闭了默认自动接管未知旧库的行为，避免错误基线掩盖结构漂移。

## 亮点四：OSS 图片上传和云端验证安全

### 当前实现

- 图片上传必须登录；头像允许普通用户上传，商品图和广告图需要管理员权限。
- 服务端限制文件为空、10 MiB 大小、声明的 MIME 类型、PNG/JPEG/GIF 文件签名、图片可解码性和 4000 万像素上限。
- 不信任客户端文件名或扩展名；服务端根据文件内容确定扩展名，并使用用途目录与 UUID 生成对象 key。
- OSS 上传设置正确 `Content-Type` 和禁止覆盖元数据，降低同名对象覆盖风险。
- 真实 OSS 生命周期探针只使用 `_validation` 隔离目录，验证上传、匿名读取、删除和删除后 404。
- 业务目录权限探针只尝试删除预先确认不存在的随机名称；当时的真实探针结果证明运行时 RAM 用户对头像、商品和广告目录的删除请求被阿里云拒绝。
- 删除方法在代码层也只接受严格格式的 `_validation` 对象名，避免测试工具越界删除头像、商品图或广告图。
- 后端生产和测试日志关闭 Apache HTTP、OSS SDK 与支付宝 SDK 的原始请求参数日志，并对常见凭据、Cookie、Token、签名和云端诊断字段统一遮挡。

### 设计取舍

应用运行账户按照最小权限原则配置。为了验证上传和读取能力，单独设计受限的验证目录；为了验证“不允许删除业务图片”，探针不上传也不选择现有对象，而是对随机且确认不存在的对象名称发出删除请求。2026-08-10 的真实探针曾验证三类业务目录的删除请求均被拒绝，但云端 RAM 策略可以在代码仓库之外被人工修改，所以每次面试演示前仍需重新执行只读权限检查，不能把历史结果描述为永久不变的云端状态。

### 测试证据

- 有效图片使用服务端唯一 key，不同用途进入不同目录。
- 空文件、超大文件、超大像素、文本伪装图片、声明类型不支持、声明 PNG 但内容为 JPEG 等情况均在调用 OSS 前被拒绝。
- 上传会设置图片类型和禁止覆盖，并确保客户端始终关闭。
- 删除严格限制在验证目录，越界 key 和嵌套路径被拒绝。
- 两项真实 OSS 检查曾显式执行并分别 1/1 通过；默认 Maven 测试不会访问真实 OSS。

### 尚未完成

业务保存失败后产生的未引用图片还没有自动过期清理机制，OSS-003 仍然活跃。因此不能声称“OSS 文件生命周期已经完整自动化”。

## 亮点六：安全边界的渐进式加固

除 OSS 外，已完成的安全改造还包括：

1. **原问题**：旧代码具体会产生什么错误，不能只说“性能不好”或“不够优雅”；
2. **方案选择**：采用了什么机制，为什么适合当前单体项目和数据边界；
3. **事务或安全边界**：哪些操作必须一起成功，哪些外部输入不可信；
4. **测试证据**：Red 阶段如何证明缺陷，Green 后断言了哪些最终状态；
5. **替代方案**：为什么没有选择悲观锁、Redis 锁、消息队列或更复杂架构；
6. **诚实边界**：当前没有完成什么，下一步如何补齐。

示例：

> 原先下单是先读库存再修改，真实并发测试中 16 个线程争抢 1 件库存却产生 16 个成功订单。我把库存充足判断和可用/冻结库存变化合并为一条 MySQL 条件更新，并把库存、订单和订单项写入放进同一事务。方案适合当前单体应用，因为库存最终数据就在 MySQL，规则也只是按数量增减，不需要额外的分布式锁。修改后补了库存不足、多商品失败、持久化失败和真实并发测试。当前只能证明这些并发场景不超卖，没有做吞吐量压测，所以不会声称达到某个 QPS。

## 维护规则

每次完成新的 FIX/FEAT 并合并到个人 `master` 后，维护者应检查本文档：

1. 从冷层交付记录和最终代码确认能力范围；
2. 更新“当前亮点与可信程度”和“当前不能写成已有能力”；
3. 只有实现、测试和合并证据齐全时，才增加或增强简历句子；
4. 测试数量只记录特定交付时的结果，不把旧数字伪装成当前永久基线；
5. 性能、并发规模和稳定性数字必须来自可复现实验；
6. 外部服务验证要区分本地替身、只读真实探针、沙箱交易和生产交易；
7. 如果后续改动使旧描述失效，应立即降级或删除对应表述，不能为了简历保留过期结论；
8. 文档不得包含账号、订单号、交易号、AccessKey、支付宝密钥、签名、Token 或任何真实 `.env` 值。

本文档持续保留在温层，不因单个开发分支完成而归档。只有被新的简历/面试材料体系完整替代时，才以 `superseded` 状态进入冷层。
