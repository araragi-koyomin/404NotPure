# 404NotPure 开发流程标准作业程序

## 目的

本文件规定项目从接受需求到合并、归档的统一流程，解决以下问题：

- 项目所有者无法快速判断当前做到哪一步；
- 多个功能或修复混在同一个未提交工作区；
- “代码已经写完”“测试已经通过”“审查已经通过”和“工作项已经完成”被混为一谈；
- 新缺陷、范围变化、分支变化和测试结果没有及时同步到 BACKLOG；
- 外部服务验证、Git 操作或破坏性操作在权限不明确时被错误执行。

本流程固定的是必须经过的检查步骤，不固定具体技术实现。事务锁、缓存方案、测试数量、类的拆分方式等仍应根据实际代码、风险和测试证据选择。

## 常用概念

- **开发批次**：一次集中交付的一组相关工作，例如“OSS 与图片上传安全整改”或“订单与库存一致性改造”。一个批次可以包含多个 BACKLOG 工作项，但必须有共同目标和清楚的非目标。
- **当前阶段**：开发批次目前所处的步骤，例如“编写测试”“实现”“完整验证”“独立审查”或“等待项目所有者确认”。
- **检查步骤**：进入下一阶段之前必须满足的条件。例如，代码实现后必须通过约定测试，才可以进入独立审查。
- **独立审查**：由没有继承实现过程结论的新 subagent 重新阅读代码、测试、文档和差异。它用于发现主开发过程可能忽略的问题，不能代替项目所有者的合并授权。
- **约定的集成分支**：本批次最终要合并到的分支。通常可能是 `main`，也可能是课程项目当前使用的 `lab4`。开始 Git 交付前必须明确记录，不能根据名称自行猜测。

## 工作角色与权限

### 项目所有者

- 决定需求目标、范围和重要取舍；
- 决定是否允许真实 OSS、支付宝或其他外部服务操作；
- 决定是否允许创建分支、提交、推送或合并 Git；
- 在分支目标、兼容行为或外部影响存在重大歧义时作最终决定。

### 主开发代理

- 在修改前检查 Git 状态和项目指令；
- 维护 BACKLOG、温层计划和冷层归档；
- 按 TDD 编写测试和实现；
- 运行与风险相匹配的验证；
- 清楚报告已完成、未完成、未执行和被阻塞的事项；
- 未经授权不提交、不推送、不合并，不执行破坏性操作。

### 独立审查 subagent

- 默认只读，不修改文件；
- 独立检查差异、调用链、测试真实性、文档和安全边界；
- 按影响程度报告问题、证据、触发条件和建议；
- 不把“没有发现问题”表述为绝对安全，也不决定是否合并。

## 标准代码开发流程

### 第 1 步：确认需求与非目标

开始前必须用常见语言写清：

- 要解决的实际问题；
- 本次包含哪些接口、模块和文档；
- 本次明确不处理什么；
- 兼容性要求；
- 完成后用什么代码行为和测试证明。

能够从仓库查明的内容先自行核实。只有会明显改变范围、数据、安全、兼容性或工作量的问题才向项目所有者确认，不能为了形式反复提问。

### 第 2 步：更新热层和温层文档

在写业务代码前完成：

1. 在 `docs/BACKLOG.md` 登记或更新工作项；
2. 在 BACKLOG 的“当前开发批次”中记录当前目标、阶段、已完成、尚未完成、阻塞和下一步；
3. 在温层计划中记录范围、TDD 顺序、验收标准、风险和开放问题；
4. 接受新需求、发现缺陷、范围变化、优先级变化或阻塞变化时，在同一次修改中更新 BACKLOG。

BACKLOG 只保存活跃状态和摘要，不应堆积完整实现过程。详细过程和证据写入对应温层计划。

### 第 3 步：确认 Git 边界

1. 执行 `git status --short --branch`，区分已有修改、未跟踪文件和本批次改动；
2. 保留所有已有用户修改，不得擅自覆盖、删除或回退；
3. 明确本批次的起始分支、开发分支和计划合并目标；
4. 创建开发分支时，在同一次变更中更新 BACKLOG；
5. 分支目标不清楚时暂停 Git 交付，不能默认合并到 `main`；
6. 未经项目所有者明确授权，不创建提交、不推送、不合并。

如果已有大量未提交修改，应先完成当前批次的审查和 Git 整理，再开始新的大型功能。不得把 OSS、安全、订单、支付和缓存等多个独立批次继续叠加在同一个无法区分的差异中。

### 第 4 步：按 TDD 开发

代码开发遵循 Red → Green → Refactor：

1. **Red**：先写能够因目标缺陷而失败的测试，实际执行并确认失败原因正确；
2. **Green**：编写让该测试通过的最小实现；
3. **Refactor**：在测试持续通过时整理命名、重复代码和结构；
4. 每增加一类行为，都要验证失败证据和通过证据，而不是一次写完全部测试后直接宣称遵守 TDD。

禁止“测试看起来很多但没有证明真实行为”的做法，包括：

- 只检查 Mock 方法调用次数，不检查最终状态或返回结果；
- 在测试中复制生产实现，再比较两个相同算法；
- 使用永远成功的断言；
- 用单元测试代替真实数据库事务、锁和并发验证；
- 用 Mock Redis 代替 TTL、序列化和失效行为验证；
- 为了通过测试而跳过失败用例或关闭关键检查。

### 第 5 步：执行分层验证

验证范围根据改动选择，但必须明确哪些已执行、哪些未执行。

#### 后端代码改动

至少考虑：

```powershell
cd back_end
mvn compile
mvn test
```

涉及事务、锁、数据库约束或 Redis 行为时，还必须运行对应的真实 MySQL/Redis 集成测试。TEST-002 已恢复并验证 Surefire 独立测试进程；后续不得用 `-DforkCount=0` 的结果冒充默认测试通过。若因诊断需要临时禁用独立测试进程，必须单独说明原因、命令和证据边界，并在交付前重新执行默认 `mvn test`。

#### 前端代码或接口契约改动

至少考虑：

```powershell
cd front_end
npm run build
```

涉及用户操作流程时，还应运行相应的页面或 API 流程检查，不能只依赖 TypeScript 编译成功。

#### Docker 配置改动

至少执行 Compose 解析检查和仓库已有的配置测试。只有四个容器实际启动、健康检查通过且前端代理成功，才能宣称完整 Compose 可用。

#### 所有改动

至少执行：

```powershell
git diff --check
```

文档改动还要检查所有 `docs/**/*.md` 的 Frontmatter、状态枚举、内部链接和行尾空白。

### 第 6 步：主开发代理自查

进入独立审查前，主开发代理必须确认：

- 实现没有超出确认范围；
- 没有覆盖用户已有修改；
- 接口和前端字段保持兼容，或兼容变化已经获得确认；
- 测试确实证明目标行为；
- 日志和文档没有密钥、密码、Token、签名或真实支付参数；
- BACKLOG 和温层计划与当前代码状态一致；
- 测试失败、未执行项和外部环境限制没有被隐藏。

### 第 7 步：独立审查

以下批次必须由新的、不了解此前实现过程的 subagent 进行只读独立审查：

- 订单、库存、支付、认证和权限；
- 真实外部服务和敏感日志；
- 数据库迁移和并发控制；
- 跨越多个模块或准备合并的大型改动；
- 项目所有者明确要求独立审查的工作。

独立审查发现问题后：

1. 主开发代理复核证据；
2. 接受的问题立即更新 BACKLOG；
3. 按 TDD 修复；
4. 重新运行受影响测试和完整验证；
5. 对修复后的差异进行新的针对性独立复核，不能继续使用修复前的“通过”结论。

### 第 8 步：项目所有者确认

审查和验证完成后，主开发代理必须报告：

- 修改文件和主要行为；
- 执行过的命令及结果；
- 独立审查结论和修复情况；
- 尚未解决的风险；
- 当前分支、目标分支和计划 Git 操作；
- 需要项目所有者决定的事项。

没有项目所有者的明确授权，不进行暂存、提交、推送或合并。

### 第 9 步：Git 交付与文档归档

获得授权后，按项目所有者确认的范围执行 Git 操作：

1. 只暂存本批次文件，不包含无关用户文件；
2. 再次检查暂存差异和敏感信息；
3. 创建清楚说明行为和测试的提交；
4. 按授权推送或合并到约定的集成分支；
5. 合并成功后，把完成证据写入冷层；
6. 从 BACKLOG 移除完成工作项；
7. 更新“当前开发批次”为下一项工作。

提交成功不等于合并成功；合并成功但没有归档，也不算流程完整结束。

## 三种适用路径

### 正常代码改动

适用于功能、缺陷、安全、交易、数据库和缓存改造。必须完整执行需求、文档、Git 边界、TDD、验证、自查、独立审查、确认和归档流程。

### 纯文档改动

如果确认没有代码、依赖或运行配置变化，可以使用简化路径：

1. 检查 Git 状态；
2. 更新 BACKLOG 和相关文档；
3. 检查 Frontmatter、内部链接、状态和行尾空白；
4. 执行 `git diff --check`；
5. 报告结果。

纯文档改动不强制运行 Maven 或前端构建，但必须明确说明未运行的原因。

### 外部服务验证

适用于 OSS、支付宝和未来公网部署：

1. 先获得项目所有者对真实外部操作的明确授权；
2. 说明操作是否会创建、修改或删除真实资源；
3. 使用隔离的验证对象、随机且确认不存在的名称或不存在的测试订单号；
4. 默认单元测试不访问真实外部服务；
5. 不输出凭据、签名、Bucket、Endpoint、对象名或云账户诊断详情；
6. 明确清理步骤和失败后是否可能残留数据；
7. 外部权限或配置检查失败时立即停止，更新 BACKLOG，不临时扩大权限绕过；
8. 怀疑凭据进入日志时立即停止使用并轮换，不继续试验。

## 必须暂停并请求确认的情况

遇到以下情况不能自行扩大范围：

- 目标分支或合并策略不清楚；
- 需要删除、覆盖、迁移或批量修改用户数据；
- 需要真实支付、真实退款或修改云端权限；
- 发现配置或日志可能包含秘密；
- 用户已有修改与当前改动直接冲突；
- 技术方案会改变现有 API、数据库兼容性或前端行为；
- 测试持续失败且原因不能从仓库或本机环境查明；
- 新问题会显著扩大本批次工作量。

暂停时应说明已经确认的事实、具体阻塞、可选方案、影响和推荐选择，不能只给出错误代码或内部工作项编号。

## 完成定义

一个工作项只有同时满足以下条件，才能从 BACKLOG 移除：

- 目标和非目标已经记录；
- 代码或文档实现完成；
- 要求的测试和验证通过；
- 必要的独立审查通过，审查问题已经修复并复核；
- 项目所有者已经确认 Git 交付；
- 已合并到约定的集成分支；
- 完成证据已经进入冷层归档；
- BACKLOG 和当前开发批次已经更新。

“代码写完”“本机测试通过”“已经提交”都只是中间阶段，不能单独作为完成结论。
