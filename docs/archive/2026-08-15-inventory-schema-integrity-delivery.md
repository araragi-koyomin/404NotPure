# DB-001B 库存结构完整性交付记录

## 目标与现状

`stockpile` 当前只有独立主键 `id`，`product_id` 既不唯一，也没有引用商品表的外键。应用创建商品时会在同一事务中创建一条初始库存，下单 SQL 也会在发现重复库存时拒绝交易，但数据库仍允许直接 SQL、旧程序或并发写入制造重复记录和无效商品引用。

2026-08-15 只读核对结果：开发库 `Tomato` 已应用 Flyway V1 基线和 V2，包含 3 个商品但没有库存；演示库 `tomatomall_demo` 已实际执行 V1/V2，包含 300 个商品和 300 条库存。两个数据库都没有重复库存、无效商品引用或负库存，`stockpile` 都只有主键索引。

2026-08-15 实施结果：V3/V4、实体映射、只读预检脚本和迁移测试已实现。开发库已迁移为 3 个商品、3 条零库存记录；演示库保持 300 个商品、300 条库存。两库的 Flyway 历史均到 V4，并且都存在 `uk_stockpile_product_id` 唯一约束和 `fk_stockpile_product` 外键。迁移前后检查只保存聚合数量、商品 ID 和结构名称，没有保存数据库密码或用户资料。

本批次目标是让数据库保证每条库存属于真实商品、同一商品最多一条库存，并把已有商品缺失的库存安全补为不可售的零库存。应用事务继续保证新建商品同时创建库存；不引入触发器、共享主键或复杂双向外键来强迫商品表必须存在子记录。

## 已确认设计

1. V3 使用一条 `ALTER TABLE` 同时增加 `uk_stockpile_product_id` 唯一约束和 `fk_stockpile_product` 外键，外键采用限制删除，不设置自动级联。
2. V3 遇到重复 `product_id` 或指向不存在商品的库存时必须整体失败；不自动累加、择一、删除或覆盖库存。
3. V4 只为没有库存的商品插入 `amount=0`、`frozen=0`，不修改任何已有库存。
4. `StockPile` 实体同步声明 `product_id` 非空和唯一；保持独立主键 `id` 和现有 Repository 泛型/API 兼容。
5. 保留下单条件原子更新及其重复库存防御，不在数据库迁移 PR 中重写已经验证的并发扣减算法。
6. 增加只读 PowerShell 预检脚本，在一个 MySQL 一致性快照中报告 Flyway 版本、索引、商品/库存数量、重复库存、无效引用、缺失库存和负库存；重复或无效引用返回失败，缺失库存标为将由 V4 补齐，负库存只警告并交给 STOCK-001。异常明细最多展示前 100 条，并明确输出列表是否截断，完整数量始终单独报告。

## 非目标

- 不清理 `PaymentInfo/payment_info`；该范围属于 DB-001C。
- 不改变库存调整接口及 `amount`/`frozen` 的业务语义；负库存缺陷由 STOCK-001 跟踪。
- 不改变商品、库存、购物车、订单或支付 API，不重写前端。
- 不自动处理重复库存，不把本机迁移结果外推为生产无停机迁移能力。

## TDD 顺序

1. Red：在只应用到 V2 的真实 MySQL 临时数据库中证明当前结构允许同商品插入两条库存，并证明预期的 V3/V4 尚不存在。
2. Red：加入全新库、正常 V2 库、重复库存、无效商品引用、缺失库存、重复运行和并发创建验收；在实现迁移前由缺少版本或约束准确失败。
3. Green：增加 V3/V4 和实体唯一映射，使迁移测试通过。
4. Refactor：复用迁移测试的临时 schema、索引和外键检查工具，保持每个测试只删除自己创建且名称带固定前缀的数据库。
5. 调整原本通过手工插入重复库存验证下单拒绝的测试：旧结构重复由迁移失败测试覆盖，迁移后重复写入由唯一约束和真实并发测试覆盖；正常下单、库存不足、回滚和防超卖证据保留。
6. 为预检脚本先写静态/行为失败测试，再实现只读查询、脱敏输出和失败退出码。

## 验收标准

- 全新数据库按顺序执行 V1～V4，Hibernate 对全部实体执行 `validate` 成功；第二次迁移执行 0 项。
- 正常 V2 数据升级后，已有库存的 `id`、`amount` 和 `frozen` 不变。
- 重复库存或无效商品引用使 V3 失败，原记录数量和值保持不变，不创建 V4 零库存。
- 缺失库存由 V4 补为且只补为一条 `0/0`；现有库存不被覆盖。
- V4 后并发为同一商品插入库存只能成功一次，最终恰好一条记录。
- 开发库迁移后为 3 个商品、3 条库存；演示库迁移后仍为 300 个商品、300 条库存。
- 商品创建/删除、正常下单、支付释放冻结库存、DATA-001 重复导入和完整 Maven 回归通过。
- 本机后端通过 Flyway 和 Hibernate 验证启动，商品/库存主链路完成验收；所有文档检查和 `git diff --check` 通过。

## 风险和回滚边界

MySQL 的结构变更不是整个 Flyway 文件级别的通用事务。V3 把唯一约束和外键放进同一条 `ALTER TABLE`，避免两项结构规则只成功一半；V4 单独执行可重复判定的补齐语句。迁移只能在预检无重复库存和无效引用后执行。实际迁移开发库和演示库前后都要保存聚合计数和约束证据，但不得在日志或文档中保存数据库密码、用户资料或支付配置。
