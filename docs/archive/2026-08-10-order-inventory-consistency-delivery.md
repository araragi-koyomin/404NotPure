# ORD-001 订单与库存一致性交付记录

## 交付范围

ORD-001 已于 2026-08-10 通过 [Pull Request #2](https://github.com/araragi-koyomin/404NotPure/pull/2) 以 squash 方式合并到个人 Fork 的 `master`，合并提交为 `39dbd59d`。本次交付只解决“创建订单并冻结库存”这一段链路的一致性，不把结论扩大到支付回调幂等、结算请求幂等、取消订单、超时解冻或完整订单生命周期。

## 关键实现

- `OrderServiceImpl.addOrder` 使用数据库事务覆盖请求校验、用户和商品读取、库存冻结、订单保存与订单项保存。任一步骤抛出异常时，已执行的库存更新和订单数据全部回滚。
- Controller 使用 Bean Validation，服务层也执行独立防御性校验。空订单、空商品列表、空商品 ID、空数量、零数量、负数量、空支付方式、损坏 JSON 和 JSON `null` 都会被拒绝。
- 同一请求中的重复商品先按商品 ID 汇总数量并排序，避免拆分数量绕过库存检查；数量相加溢出会被拒绝。
- 库存冻结使用 MySQL 条件原子更新：只有可用库存满足购买数量且商品对应唯一库存记录时，才在同一条 SQL 中执行 `amount -= quantity` 和 `frozen += quantity`。
- 原子更新返回 0 行时，服务根据库存记录数量区分库存缺失、不足和重复库存数据；重复库存数据会导致整个事务失败，避免任意选择其中一行继续下单。
- HTTP 参数错误保持现有 `Response<T>` 包装，并返回 HTTP 400，不改变 `/api/cart/checkout` 路由和前端请求字段。

## TDD 证据

Red 阶段实际证明了以下缺陷，而不是先写实现后补不会失败的测试：

- 服务层非法请求原本会先访问数据库并返回错误的业务原因。
- Controller 的 DTO 约束原本没有生效，非法请求返回 HTTP 200。
- 重复商品原本会生成多条订单项，且没有按总需求校验库存。
- 多商品下单后续失败、订单保存失败时，前面已经修改的库存原本不会回滚。
- 16 个线程争抢 1 件库存时，旧实现曾产生 16 个成功订单，证明“先读后写”不能防止超卖。
- 第一版原子更新仍可能在重复库存脏数据下选中一行继续更新；审查后增加了“只有唯一库存记录才允许更新”的 SQL 条件和真实数据库回归测试。

Green 与 Refactor 阶段完成后，测试验证业务结果、数据库最终状态、事务回滚和并发结果，不只验证 Mock 方法调用次数。

- ORD-001 定向测试：27/27 通过。
- 后端完整测试：79/79 通过，0 失败、0 错误、0 跳过。
- 修正重复库存 SQL 后，16 线程争抢 1 件库存的真实 MySQL 测试额外连续执行 3 次，全部通过。
- `mvn compile` 通过。
- `git diff --check` 通过。
- 两轮冷启动独立审查覆盖事务边界、SQL 并发语义、重复库存数据、HTTP 错误兼容和测试真实性；发现的问题已经修正并复核。

验证使用本机 MySQL。由于本机 Surefire 独立进程曾发生原生内存不足，本轮完整测试使用 `-DforkCount=0`；这只说明本轮测试通过，不代表默认测试进程问题已经解决，后续仍由 TEST-002 跟踪。

## 合并后仍然存在的风险

- ORD-002：结算请求没有跨进程幂等键。用户重复点击或客户端超时重试仍可能创建两个不同订单并分别冻结库存。
- DB-001：库存表尚未通过版本化迁移建立商品唯一约束；当前代码会拒绝重复记录，但数据库还不能从根源阻止新增重复记录。
- PAY-001：支付宝回调的金额、合法状态、并发重复通知、支付时间和支付宝交易号处理仍未完成。
- CACHE-001：商品详情缓存的未命中回填、空值保护和写后失效仍未完成。
- TEST-001：订单与库存测试已经补齐，但支付和 Redis 的可信测试尚未完成，因此该综合测试工作项仍保持活跃。
