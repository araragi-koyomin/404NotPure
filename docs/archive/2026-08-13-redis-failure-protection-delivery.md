# CACHE-003 Redis 故障保护交付记录

## 交付结果

CACHE-003 已于 2026-08-13 通过 [Pull Request #13](https://github.com/araragi-koyomin/404NotPure/pull/13) 以 squash 方式合并到个人仓库的 `master`，合并提交为 `d99cd254`。本次交付解决 PERF-001 已确认的具体故障：Redis 完全停止时，商品详情请求曾长期等待客户端连接，计划 50 QPS、10 秒的窗口内没有业务请求完整返回。

功能开发分支为 `codex/cache-redis-failure-protection`，合并后冷层归档使用 `codex/archive-cache003`。两个分支都只面向个人仓库的 `master`，没有修改只读的原多人仓库。

当前商品详情缓存故障保护行为如下：

- Redis 建立连接默认最多等待 250 毫秒，命令默认最多等待 500 毫秒；参数均可通过环境变量调整；
- 第一次确认连接失败、连接关闭或命令超时后，应用临时绕过商品缓存 5 秒，避免后续每个请求重复等待同一故障；
- 故障期间最多允许 4 个商品详情请求同时回退 MySQL，等待名额最多 50 毫秒；仍无名额时返回 HTTP 503 和统一的 `code/msg/data` 响应；
- 5 秒后只允许一个请求检查 Redis 是否恢复，其他请求继续使用受限数据库回退；
- 恢复检查先重置 Lettuce 共享连接，再用 `SCAN` 分批删除 `product:detail:v1:*`；不执行 `FLUSHDB`，不删除其他 Redis 业务键；
- 恢复清理成功后才重新开放缓存读取，防止故障期间 MySQL 已更新、Redis 中旧商品值仍被重新使用；
- 商品缓存读取、回填、更新后失效、删除后失效和广告预热使用同一故障状态；单个缓存值类型错误或反序列化失败只删除当前键，不停用全部缓存；
- Micrometer 指标记录 Redis 故障、临时绕过、数据库回退成功与拒绝、恢复尝试与成功、清理失败、当前状态和活动回退数量；
- 前端商品详情页明确显示“商品服务暂时繁忙，请稍后重试”，不自动重试。

该实现是单体应用内的故障保护，不是 Redis Cluster、Sentinel 或跨实例共享断路状态，也不承诺数据库与 Redis 强一致。

## TDD 与独立审查

开发遵循 Red → Green → Refactor：

1. 首批测试在缺少 `ProductCacheResilience`、数据库回退限制和缓存故障结果时无法编译或按预期失败；
2. 增加连接/命令超时、5 秒绕过、4 个回退名额、50 毫秒等待、HTTP 503、单恢复检查者、前缀清理和指标实现后，针对性测试转为通过；
3. 使用一个接受 TCP 连接但不返回 Redis 命令结果的可控服务，证明命令卡住时会在设定时间内回退，而不是只用 Mock 模拟异常；
4. 冷启动独立审查发现 `RedisSystemException("Connection is closed")` 没有进入全局绕过。新增失败测试后，生产代码只精确识别该异常和消息，不把所有未知系统异常错误地当作 Redis 宕机；
5. 审查还发现停机脚本在 HTTP 响应中断时可能不恢复演示商品，且商品恢复失败可能跳过测试键清理。修复后在更新请求前登记恢复责任，并分别尝试商品恢复与测试键删除，同时保留原始失败和清理失败说明；
6. 最后一次复核发现恢复轮询曾吞掉 HTTP 503、500 和网络异常。收紧后每一次轮询都必须返回业务码 `200` 和正确商品 ID，否则验收立即失败。

修复复核完成后，独立审查没有发现剩余 P0、P1 或 P2 问题。

## 兼容性与配置

- 现有商品详情路由、正常 HTTP 200 响应以及 `Response<T>` 外层保持不变；只有数据库保护容量耗尽时新增 HTTP 503；
- 配置统一记录在 `application.yml`、`back_end/.env.example` 和本机环境指南，不包含真实配置值；
- 广告热门商品预热仍然保留，但 Redis 故障绕过期间不会为了预热读取数据库；
- 缓存正常未命中继续使用原有 MySQL 商品行锁处理回填与商品更新顺序；库存扣减仍使用条件原子更新，两者用途不同；
- 恢复清理只匹配 `product:detail:v1:*`，不得改成 `FLUSHDB`。

## 尚未解决的边界

- CACHE-003 保护 Redis 基础设施故障，不解决同一热门商品缓存刚失效时多个请求重复查库的问题；该问题继续由 CACHE-002 跟踪；
- 故障第一次被观察到之前，已经同时进入 Redis 调用的少量请求可能分别经历一次失败；本次没有为了把它强行收敛成一次而串行化所有缓存读取；
- 5 秒故障状态和 4 个数据库回退名额位于单个 Java 进程内，多后端实例会分别维护状态；
- 当前 50 QPS 没有把 4 个回退名额用满，不能据此声称已经测得系统容量上限或生产级高并发能力；
- 商品键达到远高于当前 300 本的数据规模时，需要重新测量恢复扫描批量和耗时；
- Cache-Aside 仍不是数据库与 Redis 的强一致协议。正常运行时数据库提交后的单次 Redis 删除失败，旧值仍可能存活到 TTL；CACHE-003 只在确认故障恢复时清理全部商品详情键。
