# 认证授权边界与前端敏感日志交付记录

## 交付范围

SEC-011 和 SEC-001 已于 2026-08-10 通过 [Pull Request #5](https://github.com/araragi-koyomin/404NotPure/pull/5) 以 squash 方式合并到个人 Fork 的 `master`，合并提交为 `21463e4f`。本批次严格按“先删除并防止前端敏感响应日志，再收紧后端认证和资源所有权”的顺序完成。

本次交付解决的是商城现有账户、购物车和支付表单链路中的具体越权与身份混淆风险，不宣称已经建立覆盖所有业务的完整权限平台。跨站请求伪造（CSRF）防护、购物车正数规则、积分发放规则、支付同步返回页、后端异常堆栈日志和完整订单生命周期仍由独立活跃任务跟踪。

## SEC-011：前端敏感日志保护

- 删除登录成功路径中包含 token 的完整登录响应，以及包含角色、电话、邮箱和地址等资料的账户响应日志。
- 冷启动审查继续发现并删除商品、广告和图片页面中 11 处完整请求或响应正文日志，避免把提交对象、图片响应或服务端错误正文写入浏览器控制台。
- 增加覆盖 `front_end/src` 中 `.ts` 和 `.vue` 文件的静态安全检查，识别常见 Promise、`await`、完整 Axios 错误对象、`res.data`、`err.response` 和序列化提交对象输出；固定事件名、错误类别和 HTTP 状态仍可用于必要诊断。
- 增加脱敏错误描述工具，只保留错误名称、错误码和 HTTP 状态，不直接采用可能携带上游正文的任意 `message`。
- 修复退出失败仍显示成功的问题：只有服务端退出成功后才清理前端状态并跳转；失败时保留登录状态，允许用户重试。

静态检查是针对当前常见变量名和语法结构的启发式防回归保护，不是 JavaScript 全语义证明。未来引入响应别名、解构或统一日志辅助函数时，必须同步扩展检查用例。

## SEC-001：认证与资源所有权

- MVC 拦截器只精确放行公开路由，不再按 `/api/orders`、`/api/cart` 或相邻字符串前缀整体放行；支付宝异步通知与同步返回入口继续保持所需兼容。
- `TokenUtil` 统一读取名为 `token` 的 HttpOnly Cookie 和同名请求头。任一单独来源或两个相同来源可以认证；值不同、重复冲突或无效令牌统一拒绝，避免拦截器和控制器采用不同身份。
- JWT（登录身份令牌）签名密钥从 Java 源码迁移到 `JWT_SECRET` 环境变量；缺少配置时拒绝启动，不再回退到仓库内置密钥。Cookie 与 JWT 使用同一可配置有效期。
- CORS（浏览器跨来源访问规则）从反射任意 Origin 改为明确的前端来源白名单，认证 Cookie 增加 `SameSite=Lax`。
- 注册时由服务端固定普通用户角色，资料更新保留数据库中的既有角色；账户资料和积分读取只允许当前账户通过自己的用户名或手机号访问。
- 购物车查询、添加、更新、删除和结算都从已验证令牌取得当前用户；更新和删除还核对数据库中的购物车条目归属，普通用户和管理员均不能修改其他账户的条目。
- 支付表单只允许订单本人为自己的 `PENDING` 订单生成。支付宝 SDK 调用被隔离到 `PaymentFormGateway`，匿名、跨用户、管理员代付、订单不存在和非法状态请求都会在进入 SDK 前被拒绝。
- 商品、库存、广告和受保护图片写接口继续保留服务端管理员校验；普通用户前端不显示商品管理入口，但菜单隐藏不替代服务端权限判断。

## TDD 与独立审查证据

测试驱动开发的 Red 阶段（先写能够复现缺陷的失败测试）证明了以下旧行为：

- 登录页两处敏感响应输出及其他 11 处请求或响应正文输出会被新增检查报告；
- 匿名购物车和支付表单被旧前缀规则放行，请求头单独认证无效，冲突 Cookie/请求头没有统一拒绝；
- 其他普通用户能够修改或删除购物车条目，管理员也能删除他人条目；
- 旧支付控制器直接调用支付宝 SDK，无法证明越权请求在外部调用前终止；
- 其他账户可以读取资料或设置积分，且旧实现没有可靠的本人资源边界；
- 任意 Origin 可以得到带凭据跨域响应，Cookie 与 JWT 的有效期不一致。

Green 阶段（实现修复后测试通过）完成最小权限收紧。随后由不了解实现过程的独立 subagent 进行冷启动只读安全审查，两轮复核继续发现并修复完整 Axios 错误对象日志、退出失败假成功、剩余请求/响应正文日志、过宽错误消息契约和相邻路径前缀放行等问题。最终极窄复核没有发现剩余阻断问题。

## 合并后仍然存在的边界

- SEC-012：Spring Security 的 CSRF 开关仍关闭。当前已有明确 CORS 白名单与 `SameSite=Lax`，但尚未建立前端 CSRF token 协议及登录、注册、支付宝通知的兼容例外。
- SEC-013：全局异常处理仍可能对预期业务拒绝打印完整后端调用栈，尚未建立结构化脱敏日志契约。
- CART-001：购物车添加和更新仍需统一拒绝零数、负数及超过业务上限的数量。
- ACCT-001：通用积分修改入口当前保持拒绝，后续必须先定义可信的积分发放业务规则。
- PAY-002：支付宝同步返回页仍必须改为查询服务端订单状态，不能只相信浏览器参数。
- PAY-003：尚未执行沙箱买家虚拟付款和公网异步通知的一次性端到端验收。
- FE-002：冷启动首次点击疑似重载在 Vite 依赖预热后无法复现，没有代码修复证据，继续作为低优先级观察项。
