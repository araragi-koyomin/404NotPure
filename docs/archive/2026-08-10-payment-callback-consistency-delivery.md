# 支付回调一致性与数据库迁移交付记录

## 交付范围

DB-001A、PAY-001、SEC-009 和 SEC-010 已于 2026-08-10 通过 [Pull Request #3](https://github.com/araragi-koyomin/404NotPure/pull/3) 以 squash 方式合并到个人 Fork 的 `master`，合并提交为 `dca1acd9`。

本次交付完善支付宝异步通知进入系统后的可信校验、并发幂等、订单状态与冻结库存事务一致性，并建立支付字段所需的 Flyway 迁移路径。它不包含支付表单订单所有权、同步返回页服务端状态确认、待支付订单取消/超时关闭、退款、清结算、多支付渠道或真实资金生产环境。

## 关键实现

- 回调在 RSA2 验签后核对通知 `app_id`、`seller_id`、订单号、支付宝交易号、订单金额和交易状态；只支持 `TRADE_SUCCESS` 与 `TRADE_FINISHED`。
- 金额由数据库订单计算结果决定，回调金额通过 `BigDecimal.compareTo` 比较，不依赖字符串格式或客户端价格。
- `PENDING -> PAID` 使用带来源状态条件的数据库更新决定唯一处理者；竞争失败后锁定读取最新订单，只有同一支付宝交易号的已支付通知按幂等成功处理。
- 支付宝交易号通过数据库唯一索引防止跨订单重复使用；支付完成时间保存到独立 `paidTime`，不覆盖订单创建时间。
- 订单状态、支付结果和全部商品冻结库存释放位于同一个 MySQL 事务。任一商品释放失败时，前面已经执行的订单和库存修改全部回滚。
- 冻结库存释放使用 `frozen >= quantity` 条件更新，并拒绝同一商品存在多条库存记录的脏数据；库存商品数据库唯一约束仍由 DB-001 后续完成。
- Flyway V1 建立当前完整 schema 基线，V2 增加支付完成时间和唯一支付宝交易号；Hibernate 从自动改表切换为 `ddl-auto: validate`。
- `baseline-on-migrate` 默认关闭。来源不明的非空数据库不会被自动标记为 V1；只有备份并人工核对与 V1 一致的旧库可以临时显式开启一次。

## TDD 与审查证据

支付 Red 阶段证明旧实现存在金额不一致仍支付、非法状态直接变为 `PAID`、支付时间覆盖创建时间、不同交易号被误认为重复通知、交易号可跨订单复用、并发通知结果不可验证等缺陷。Green 后使用条件状态更新、唯一约束、锁定重读和事务化库存释放解决。

冷启动审查进一步发现并修复：

- 回调只验签但未核对应用与收款方；
- 未接受支付宝的 `TRADE_FINISHED` 成功状态；
- Flyway 自动基线若永久开启可能错误接管任意非空数据库；
- 并发测试需要多个真实外层事务先读取同一 `PENDING` 快照后再竞争；
- 多商品回滚需要在后续商品失败前真实完成前一商品释放；
- 沙箱探针曾允许任意网关和通用成功响应；
- 支付宝 SDK 的 `sdk.biz.err` logger 会输出 APPID、随机订单号和原始业务参数。

所有审查问题均完成修复和针对性复核，最终未发现剩余 P0-P3 阻断问题。

## 外部支付验收边界

本轮没有建立支付宝服务器可访问的公网 `notify_url`，因此没有实际创建或支付沙箱订单，也没有把分层验证描述为真实异步支付端到端闭环。项目所有者确认个人项目和面试展示不要求固定公网 IP 或长期部署。

后续 PAY-003 在 SEC-001 支付表单所有权和 PAY-002 同步返回页完成后，使用一次临时 HTTPS 公网入口完成沙箱买家虚拟付款、支付宝真实异步通知、本地 `PAID` 状态和冻结库存释放验收；完成后立即关闭公网入口。该任务不扩展真实资金、退款、清结算、多支付渠道或分布式事务。

## 合并后仍然存在的风险

- SEC-001：`/api/orders` 前缀认证边界过宽，支付表单缺少订单所有权校验。
- PAY-002：同步返回页仍可能仅凭浏览器参数显示成功和清理购物车，必须改为查询服务端订单状态。
- PAY-003：真实沙箱买家付款和支付宝异步通知端到端闭环尚未执行。
- ORD-003：待支付订单没有取消和超时关闭，冻结库存可能长期占用。
- DB-001：库存商品唯一约束和遗留 `PaymentInfo/payment_info` 清理尚未完成。
- CACHE-001 / TEST-001：Redis Cache-Aside 和真实 Redis 行为测试尚未完成。
