# CART-001 购物车数量与库存状态交付记录

## 目标与实际缺陷

当前 `POST /api/cart` 会把数量直接写入购物车，没有检查正数或库存上限；`PATCH /api/cart/{cartItemId}` 只检查数量是否超过 `StockPile.amount`，因此仍会接受 0 和负数。两个请求 DTO 使用基本类型 `int`，缺失字段也会变成 0。数据库 `carts.quantity` 只有非空和默认值，没有正数检查；同一用户、同一商品也没有组合唯一约束，并发加入可能产生重复记录。

前端还错误地使用 `amount - frozen` 计算可用库存。项目库存语义已经固定为 `amount` 表示当前可用库存、`frozen` 表示待支付订单已经冻结的库存；下单时两者已经同步执行 `amount -= quantity`、`frozen += quantity`，因此购物车和商品详情必须直接使用 `amount`。

本批次让添加和修改数量都只接受严格 JSON 正整数且不超过查询时的 `amount`；购物车不冻结库存，最终并发安全仍由 ORD-001 在结算时执行的 MySQL 条件原子更新负责。

## 已确认设计

1. `productId` 和 `quantity` 使用可区分缺失值的包装类型，并通过购物车局部的严格整数反序列化拒绝小数、数字字符串、布尔值、空值和缺失字段；不修改全项目 ObjectMapper。
2. Controller 使用 Bean Validation 在服务调用前拒绝缺失、0 和负数；服务层保留相同防御性校验，直接调用服务也不能绕过。
3. 添加和修改都要求 `quantity <= StockPile.amount`。该检查只改善即时反馈，不预留库存；结算时必须重新执行数据库原子库存检查。
4. 再次加入已存在商品继续返回冲突，不累加、不覆盖。普通查询负责友好提示，V5 的 `(user_id, product_id)` 唯一约束负责并发最终保证；只把明确命中该约束的数据库异常转换为相同冲突响应。
5. V5 使用一条 `ALTER TABLE` 同时增加 `CHECK (quantity > 0)` 和 `(user_id, product_id)` 唯一约束。历史非正数或重复记录使迁移失败，不能自动改成 1、合并或删除。
6. 增加只读迁移前检查脚本，在同一一致性快照中输出购物车总数、非正数数量、重复组合数量、前 100 条异常 ID 和截断状态；不得输出用户名、电话、密码、Token 或其他资料。
7. `GET /api/cart` 批量读取库存，为每项新增向后兼容的 `availableStock` 和 `stockStatus`：库存足够为 `AVAILABLE`，库存记录存在但不足为 `INSUFFICIENT`，库存记录异常缺失为 `UNAVAILABLE`。
8. 一个商品缺少库存记录时不阻断整个列表；该商品按不可结算显示。添加或修改遇到缺失库存则返回系统数据异常，不自动创建库存。
9. 前端保留库存不足的原购物车数量，显示明确提示、禁用结算勾选并让全选跳过；仍允许降低数量或删除。修改失败后显示具体原因并重新加载购物车，恢复数据库实际值。
10. 现有业务错误继续使用 `Response<T>` 兼容模式；参数格式或 Bean Validation 失败使用 HTTP 400。商品重复和库存不足使用业务码 `409`，全项目 HTTP 状态语义另行治理。

## 非目标

- 不在购物车阶段扣减或冻结库存，不宣称购物车校验可以防止超卖。
- 不自动修改或删除库存后来不足的购物车记录。
- 不处理支付成功后的购物车清理；浏览器返回页可信状态与清理由 PAY-002 处理。
- 不实现订单取消、超时关闭、结算请求幂等、支付宝端到端验收或管理员库存调整规则。
- 不引入 Vitest、Vue Test Utils、Playwright 或 Cypress；前端行为使用构建检查和真实 Chrome 验收，如实记录自动化覆盖边界。
- 不统一全项目 HTTP 错误状态，不扩展废弃的 AI assistant。

## TDD 顺序

1. Red：Controller 契约测试证明缺失、空值、0、负数、小数、数字字符串和布尔值当前未被稳定拒绝，并验证非法请求不会调用服务。
2. Red：真实数据库服务测试覆盖正常添加/修改、超过库存、0/负数、缺失库存、重复加入和失败后购物车/库存保持不变。
3. Red：在只到 V4 的真实 MySQL 临时库证明当前允许非正数和重复用户商品组合，且 V5 两项约束不存在。
4. Red：增加正常 V4 升级、非正数拒绝、重复记录拒绝、重复迁移、Hibernate 全实体验证和两个并发请求加入同一商品；实现前由缺少约束或最终两条记录准确失败。
5. Red：先为预检脚本加入 READY、BLOCKED、100 条明细边界和脱敏输出测试，再实现单次一致性快照检查。
6. Red：真实 MySQL/MockMvc 验证列表的三种 `stockStatus`、一个异常商品不阻断其他商品，以及库存批量读取不随购物车条目逐条请求。
7. Green：完成最小后端、V5、预检和前端实现；Refactor 阶段统一数量校验、库存状态转换和约束冲突识别。
8. 回归：执行定向测试、完整 Maven、前端敏感日志检查、`npm run build`、真实数据库迁移前后检查和 Chrome 主链路验收。

## 验收标准

- 添加和修改只接受严格 JSON 正整数；非法请求为 HTTP 400、业务码 `400`，服务未被调用且数据库不变。
- 数量超过当前 `amount` 时返回稳定库存冲突，购物车原值和 `amount/frozen` 均不变。
- 同一用户、同一商品普通重复加入和并发重复加入都最多产生一条记录；并发失败方获得稳定的已存在响应。
- 全新库执行 V1～V5 并通过 Hibernate `validate`；正常 V4 数据升级保留购物车主键和数量；异常数据阻止 V5 且不留下单项约束；重复迁移执行 0 项。
- 预检脚本对正常库返回 `READY`，对非正数或重复组合返回 `BLOCKED`，完整计数和前 100 条边界有测试且输出不含用户资料。
- 购物车列表通过批量库存查询返回 `availableStock` 和三种状态；缺失库存商品不可结算但不阻断其他商品。
- 商品详情和购物车不再计算 `amount - frozen`；库存不足商品保留、提示明确、不能勾选，全选跳过；失败修改后页面恢复数据库值。
- 后端完整测试、前端构建、适用的真实 MySQL 验证、浏览器验收和 `git diff --check` 全部通过。

## 当前环境与边界

2026-08-15 只读检查显示开发库 `Tomato` 和演示库 `tomatomall_demo` 的购物车均为 0 行，没有非正数记录或重复用户商品组合。该结果只说明本机当前无需清理，不替代对其他数据库的迁移前检查。Windows 8080 保留端口问题继续由 RUN-002 跟踪；需要应用启动验收时可使用不冲突的本机端口或容器内部访问，不把端口映射失败误写为 CART-001 失败。

## 2026-08-15 实现与验证记录

本批次严格执行先写失败测试、再实现修复的 TDD 顺序。Controller 严格输入测试在旧代码上 22 项中有 19 项因错误返回 HTTP 200 而失败；真实服务与数据库测试证明旧实现会保存超库存或非法数量、列表没有库存状态；V5 迁移测试在实现前 5/5 失败，因为只有 V1～V4 且数据库仍允许非正数量与重复用户商品组合。随后才加入局部严格整数反序列化、Bean Validation、服务层防御性校验、库存上限、批量状态查询、V5 和前端行为。

独立冷启动审查发现并修复了以下测试或实现缺口：

- 原非正历史数据测试同时包含重复用户商品组合，可能只由唯一约束触发失败；修正后使用不同业务键，并在 V5 成功后实际证明 0 和负数写入被 MySQL 拒绝。
- 原并发加入测试不能保证两个事务都通过普通查询；修正后的测试用只存在于测试上下文的插入屏障，证明两个事务都到达真实 Repository 写入，再由 `uk_carts_user_product` 使一方稳定返回业务码 `409`，最终只有一条记录。
- 列表测试同时验证三个库存状态、一次批量 `findAllByProductIdIn`，并禁止逐项调用 `findByProductId`；PATCH 缺失库存也验证业务码 `500` 和原数量不变。
- 前端 `ElInputNumber` 曾错误使用 `@change.stop`；Element Plus 的 change 参数是数字，Vue 会尝试调用不存在的 `数字.stopPropagation()`，导致 PATCH 根本不发出。当前已移除该修饰符；商品卡片点击逻辑本身会排除数量控件。只有不可结算商品时，“全选”也不再错误显示为已选中。

审查修复后的最终后端默认回归在 Maven 3.9.9、Java 17、真实 MySQL 8 和 Redis 6 下为 45 个测试类、292 项，失败 0、错误 0、跳过 0。固定 1 GiB 测试容器峰值约 565 MiB，没有被系统因内存不足终止；宿主机最低剩余约 5.32 GiB。定向真实 MySQL 结果包括迁移 5/5、并发与服务防御 7/7、购物车 HTTP/所有权/库存状态 15/15。迁移前检查脚本为 3/3，`Tomato` 与 `tomatomall_demo` 均已迁移到 V5，约束存在且只读预检为 `READY`。

前端 `npm run build` 成功转换 1623 个模块，最终购物车 bundle 不再包含错误的 change `.stop`。既有的缺失背景资源、CSS `//` 注释和约 987 KB 主分包警告仍由 FE-001 跟踪，不属于本批次新增失败。

项目所有者随后明确允许启动 Chrome。验收后端使用 `127.0.0.1:9000`，前端使用 `127.0.0.1:5174`。自动控制插件仍对本机 `/api` 请求明确返回 `ERR_BLOCKED_BY_CLIENT`，授权不能覆盖插件内部 URL 安全策略，因此不能伪造浏览器自动验收结果。

项目所有者改用 Codex 内置浏览器后，登录控制台暴露出一个真实前端配置缺陷：`main.ts` 将 Axios 根地址固定为 `http://localhost:8080`，而本机 8080 位于 Windows 保留端口范围，专用后端只能映射到 9000，浏览器因此得到 `ERR_CONNECTION_REFUSED`。修复将根地址改为同源，由已有 Vite `/api` 代理按照 `VITE_API_TARGET` 转发；没有把本次临时端口 9000 永久写入源码。修复后 `npm run build` 再次成功转换 1623 个模块，通过 `http://127.0.0.1:5174/api/products` 的请求返回 HTTP 200，临时账户通过同一代理登录返回业务码 `200` 并设置一个 HttpOnly 登录 Cookie；验证过程没有输出 Cookie 或 JWT 内容。

项目所有者随后在 Codex 内置浏览器完成页面验收，并确认以下五项均无问题：库存充足商品数量修改成功；修改为超过可用库存时显示后端原始错误并恢复数据库数量；原本库存不足的商品降低数量后恢复为可选择；缺失库存记录的商品可以删除；全选只选择可结算商品。该结果补齐了构建检查无法证明的真实 Element Plus 数量输入、错误提示、重新加载和勾选状态行为。

验收后已按精确账户 ID、用户名、商品 ID 和专用标题清理临时账户、3 件商品、购物车、库存及可能的关联记录，清理查询确认账户、商品、购物车和库存剩余数量均为 0；三个专用商品缓存 key 也单独删除，没有使用 `FLUSHDB`。只停止 `404notpure-cart-frontend` 和 `404notpure-cart-backend` 两个验收容器，MySQL 与 Redis 保持健康运行。
