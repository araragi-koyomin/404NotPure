# CACHE-002 热门商品单次回填交付记录

## 交付结果

CACHE-002 已于 2026-08-14 通过 [Pull Request #15](https://github.com/araragi-koyomin/404NotPure/pull/15) 以 squash 方式合并到个人仓库 `master`，合并提交为 `28b41ad4`。功能分支为 `codex/cache-hotspot-single-flight`，合并后的文档归档分支为 `codex/archive-cache002`。

本次交付解决一个经过 PERF-001 测量确认的问题：Redis 正常运行但同一热门商品缓存刚失效时，多个并发请求会分别查询 MySQL，并在商品行的悲观写锁上排队。CACHE-002 在单个 Java 后端进程内按商品 ID 合并这类请求，只让一名负责人进入独立数据库事务、读取完整商品详情并回填 Redis，其他请求最多累计等待 500 毫秒，随后重新读取 Redis。

## 实现与设计边界

- 缓存命中、请求协调和等待都在数据库事务外执行，不占用数据库连接等待负责人。
- 数据库加载位于独立 Spring Bean 的公开事务方法中；负责人取得商品行悲观写锁，读取商品、规格和详情图，并在释放锁前回填缓存。
- 等待时间是一次商品请求累计最多 500 毫秒。等待者被唤醒后若 Redis 仍未命中，只能使用原截止时间的剩余部分，不能重新获得完整等待时间。
- 等待超时或线程被中断时返回统一 HTTP 503；线程中断标记会恢复。负责人失败会把同一个失败结果通知本批等待者，并删除协调记录，后续请求可以重新尝试。
- Redis 基础设施故障不进入 CACHE-002，而是继续交给 CACHE-003 的最多 4 个数据库回退名额、50 毫秒名额等待和 HTTP 503 保护。
- 该协调状态只存在于单个 Java 进程。多个后端实例会各自最多产生一名负责人，不是 Redis 分布式锁，也不能描述为集群全局只查询一次。

## TDD、自动化测试与独立审查

开发遵循“先写能够复现缺陷的失败测试，再实现修复”的顺序。除主要请求合并行为外，测试和审查推动修复了以下容易被忽略的边界：

- 请求在第一次检查截止时间后暂停，旧协调记录随后被删除时，已经过期的请求不得成为下一名负责人；
- 合法的纳秒截止值恰好为 0 时不能被误认为“尚未初始化”，并覆盖 `System.nanoTime()` 负值与跨最大值环绕；
- 新负责人登记后若发现已经超时，必须先通知可能已经附着的等待者，再有条件地删除自己的协调记录；
- 正式脚本必须固定 100 个虚拟用户、每人一次并等待共同起跑，不能用共享迭代冒充 100 人同时请求；
- 性能模式切换必须重新构建当前后端源码，从运行中后端指标核对实际开关，并在突发期间持续采样数据库连接池等待；
- 先前停止的指标辅助容器必须在模式切换时自动启动。该问题由正式运行在发出并发请求前发现，随后先增加失败脚本测试，再修复两个模式切换脚本。

## 正式热点对照数据

## 与 CACHE-003 的关系和未验证范围

CACHE-002 和 CACHE-003 解决不同问题：CACHE-002 处理 Redis 正常时热门商品缓存刚失效造成的重复数据库查询；CACHE-003 处理 Redis 连接失败、命令超时或完全停止时的有界数据库回退和恢复。

当前有一项受控 Spring 集成测试模拟“CACHE-002 等待者醒来后发现 Redis 基础设施故障”，并证明请求会转入 CACHE-003 的数据库回退限流器，而不是绕过其 4 个名额和 50 毫秒等待保护。该测试使用测试替身制造故障结果，没有真实停止 Redis。

CACHE-003 以前的独立真实验收在 50 QPS、10 秒 Redis 完全停止期间完成 501 个请求，P99 为 506.81 毫秒、业务错误和丢弃均为 0，并在 Redis 重启后 2.879 秒完成恢复；CACHE-002 本次六轮热点对照全部在 Redis 正常时执行。这两组数据不能拼接成“当前版本已经完成 CACHE-002 与 CACHE-003 真实综合压测”。尚未执行的完整链路是：CACHE-002 开启、Redis 真实停止、CACHE-003 自动保护、Redis 恢复并清理商品键、CACHE-002 随后重新参与热点回填。

CACHE-003 没有独立关闭开关。它是 Redis 故障时必须保留的安全保护，本次没有为了形成四种开关排列而增加容易误用的关闭模式。

## 可以陈述的结论

可以陈述：在固定本机、300 本演示商品、正常 Redis 和单后端实例的 100 请求热点突发中，CACHE-002 把每轮 MySQL `SELECT` 从 303 次降至 6 次、商品行锁等待从 99 次降至 0，并显著降低了该场景的 P95/P99 三轮中位数。

不能陈述：已经测得生产容量、已经实现多实例全局单次回源、CACHE-002 与 CACHE-003 的当前版本真实停机复合链路已经验收，或一次本机结果可以直接代表云端生产环境。
