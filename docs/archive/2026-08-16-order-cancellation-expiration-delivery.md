# ORD-003 订单取消与超时关闭交付记录

## 交付目标

旧订单只有 `PENDING`（待支付）和 `PAID`（已支付）两种状态。下单会把可用库存移动到冻结库存，但用户不付款时没有取消或超时关闭入口，冻结库存会长期无法重新出售。

本批次新增用户主动取消和后台超时关闭，并保证订单状态改变与库存恢复一起提交或一起回滚。支付、取消和关闭并发到达时，数据库只能允许其中一个方向从 `PENDING` 成功更新，避免同一订单重复释放冻结库存。

## 已实现的业务规则

1. 新增 `POST /api/orders/{orderId}/cancel`。只有订单所有者可以调用；匿名用户、其他用户和管理员替他人取消都会在修改订单前被拒绝。
2. 新增 `CANCELLED`（到期前由用户取消）和 `CLOSED`（达到或超过待支付期限后关闭）。`PAID`、`CANCELLED` 和 `CLOSED` 都是最终状态。
3. 待支付期限默认 30 分钟。用户在到期前取消进入 `CANCELLED`；恰好到期或已经过期时，同一个取消请求改为关闭并进入 `CLOSED`。
4. 重复取消已经取消或关闭的订单返回幂等成功，不再修改库存；已经支付的订单返回业务冲突。
5. 取消或关闭在同一事务中按商品 ID 顺序执行 `amount += quantity`、`frozen -= quantity`。任何商品恢复失败都会回滚订单状态和此前已经执行的库存修改。
6. 支付通知、用户取消和自动关闭都执行带 `status='PENDING'` 条件的数据库更新。只有更新到一行的事务取得处理权，其他并发事务读取最新状态后按重复请求或状态冲突处理。
7. 后台任务默认每 60 秒扫描一次，每批最多选择 100 个到期订单。每个候选订单通过 Spring 代理进入独立事务，一个异常订单不会回滚之前成功关闭的订单，也不会阻止后续订单继续处理。
8. 支付表单使用订单创建时间加 30 分钟得到的绝对到期时刻，并传给支付宝 `time_expire`；重复打开支付页面不会重新获得 30 分钟。已经到期时先在本地关闭订单，不再生成支付表单。

## 数据库迁移

Flyway V6 使用一条 MySQL `ALTER TABLE` 同时增加：

- `cancelled_time`：用户取消完成时间；
- `closed_time`：订单超时关闭时间；
- `(status, create_time, order_id)`：后台查找到期待支付订单的索引；
- 四种合法状态的检查约束。

现有 MySQL 字符排序规则默认不区分大小写，普通 `status IN (...)` 会把 `pending` 或 `Paid` 当成合法值，而 Java 枚举只接受精确大写。V6 因此使用 `CAST(status AS BINARY)` 做区分大小写的检查，防止这类订单既无法正常处理、又长期占用冻结库存。

迁移不自动修改未知历史状态。只读预检脚本在同一个数据库一致性快照中检查当前 Flyway 版本、失败迁移、未知或空状态、缺少创建时间的待支付订单、无订单项、非法数量、缺失库存和冻结库存不足；发现异常时报告 `BLOCKED`，由维护者先确认数据含义，不能自行猜测如何修复。

本机 `Tomato` 和 `tomatomall_demo` 曾在 V6 尚未合并时应用过旧校验值。修正区分大小写规则后，两库只修改约束定义并执行官方 Flyway `repair` 对齐校验值，没有修改业务订单或库存；最终均为 V6、失败迁移 0、未知状态 0、预检 `READY`。

## 独立审查与修复

不了解实现过程的独立审查重点检查了数据库状态约束、支付与关闭竞争、批处理事务、权限边界和测试隔离。审查发现并推动修复了以下问题：

- 状态检查和迁移前检查最初使用 MySQL 默认的不区分大小写比较，可能接受 Java 无法识别的状态；现已改为精确大小写并增加真实迁移测试。
- 迁移前检查最初没有阻止失败的 Flyway 记录或错误的起始版本；现已把二者纳入 `BLOCKED` 判定。
- 原测试缺少支付与自动关闭竞争、匿名和管理员权限、真实逐单事务提交证据；已分别补充。
- 后台调度最初没有在性能配置中明确关闭，可能污染缓存压测 SQL 和延迟；`application-perf.yml` 现已关闭该任务。
- 一版批处理集成测试可能查询共享开发库中的其他历史订单；最终测试改为只向处理器提供本用例创建的 ID，同时保留真实服务代理和真实数据库事务。

针对性复核确认上述问题修复后未发现剩余 P0、P1 或 P2 缺陷。这里的 P0～P2 分别表示会造成严重数据破坏、阻止主要功能交付或显著削弱正确性证据的问题等级。
